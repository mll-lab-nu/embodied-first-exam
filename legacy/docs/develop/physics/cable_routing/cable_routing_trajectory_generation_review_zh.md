# Cable Routing 轨迹生成方案 Review + 下一步计划

> 日期：2026-07-08
> 目的：评估当前 cable routing 轨迹方案是否适合**批量/可复现生成**，并把用户提出的"相切圆弧拼接"方案整理成可执行计划。
> 关联迭代记录见 `cable_routing_devlog_zh.md`。

---

## 1. 当前方案是什么

`planning/cable_routing_planner.py` 的 `_smooth_route_targets`：`routing.smooth_route=true` 时，取 config 里手写的 `endpoint_oracle_waypoints`，用**向心 Catmull-Rom(α=0.5)**样条重采样成平滑匀速曲线，保留手写点的形状。

走过的弯路（都记在迭代 log 里）：
1. 抽象 left/right 半绕 S → 绳子没缠上。
2. 按"北过 P1 / 东南绕 P2"实时画圆 → **贴内侧挤进去卡住**（绳子够长 0.73m，不是长度问题）。
3. 放大圆 + 从底部入 → 内侧不卡了，但**机械臂前臂横扫 P2**（底座在西，EE 兜到 P2 东侧时前臂横穿 pole，净空只有 0.01~0.05m）。放大圆反而更糟。
4. 定案：**放弃从零画圆，改为平滑已验证的手写路径**（手写大低回环本身是机械臂安全的）。

---

## 2. 核心结论：当前方案**不适合批量生成**

一句话：**`_smooth_route_targets` 现在是个"平滑器"，不是"生成器"。**

原因：
- 它平滑的是 config 里**手写死的绝对坐标** `endpoint_oracle_waypoints`——这是人为针对**当前这一个固定 P1/P2/C 布局**、跨很多轮调出来的（config 里那串密集 P2 回环 + 入槽尾段就是证据）。
- 一旦 `seed` 改变 fixture 布局（`generation/cable_routing_generator.py` 里已经写明"seed 预留给未来的 fixture 随机化"），这串手写点就**全错了**，样条只是把一条错的路抹平。
- 而 `generation`/`planning` 分层的**全部意义**就是"按 seed 生成可复现变式"。所以：
  - ✅ 对**当前这个确定性布局**：能出一条平滑、匀速、机械臂安全、能真绕上的路（够用）。
  - ❌ 对**批量/随机布局**：完全不行——它无法为没被手调过的布局生成路径。

换句话说：手写点恰恰是这套架构想**消灭**的东西，我们现在只是把它抹平了，没消灭它。

---

## 3. 真正的矛盾：布局自适应 vs 机械臂可行

试过的两条路正好各占一头：

| 方案 | 布局自适应(可批量) | 机械臂/pole 体积安全 |
| --- | --- | --- |
| 从零画圆（实时按 pole 位置算） | ✅ | ❌ 前臂横扫 P2 |
| 平滑手写路径（Catmull-Rom） | ❌ 死绑手写坐标 | ✅ 沿用验证过的形状 |

**难点不在"画一条绕过 pole 的几何线"**（那不难），**而在"机械臂本体能物理执行、且不撞 pole/自身"**。底座在西侧这个约束，让"绳子拓扑上要绕 P2 远侧"和"机械臂够不着/会撞"直接冲突。纯几何路径生成器解决绳子拓扑，但不管机器人可行性——这俩是耦合的。

---

## 4. 下一步计划：相切圆弧拼接生成器（用户方案）

用户提议：**以每个 pole 为中心画半径不等的圆，圆之间相切；planner 沿圆弧走，到相切点顺势转移到下一个圆，整条轨迹 = 圆弧拼接。**

这是正确方向——它同时给到自适应 + 平滑 + 可复现。落地要点与开放问题：

### 4.1 优点
- **实时按 pole 位置算**（可批量）。
- **弧 + 相切转移 → 天然 C1 平滑**，无尖点。
- 参数化（每个圆的半径、绕向），易复现、易调。

### 4.2 需要解决的设计问题
1. **半径耦合约束**：两圆外相切 ⇔ 圆心距 = r1+r2。当前 d(P1,P2)≈0.243m，所以 r1+r2 必须 =0.243（不是自由参数，是被布局锁死的一条约束）。多 pole 时是一串约束，需要一个求解/分配规则（例如按"需要绕多大"分配半径）。start 和 C 作为半径 0 的"圆"或端点，用切线接入。
2. **相切点在圆心连线上、落在两 pole 之间（gap/内侧）**：外相切的切点在 P1-P2 之间。轨迹在此转移 = 会经过内侧 gap。要确认这不会重演"贴内侧卡住"（可能需要内相切、或把切点抬高/绕开）。
3. **绕哪一侧（inner/outer）** 仍要显式决定，来匹配 `target_signature`（P1:left / P2:right）和绳子实际缠绕方向。
4. **机械臂体积（最关键，圆弧方案不会自动解决）**：弧走对了，EE 兜到 P2 东侧时前臂照样可能横穿 pole。所以生成器必须把"机械臂可行/净空"当**显式输入**，而不是指望几何自动满足。可选：
   - 启发式：优先选"让 EE 留在朝底座一侧 / 压低(南)"的弧向，使前臂从 pole 南侧掠过（手写路径正是这么做的）。
   - 或加一个轻量碰撞/可达检查（前臂用 3D 线段而非我现在的 2D 代理，真实 Franka 肘部抬高，2D 代理会高估碰撞）。
   - 或约束**任务布局**本身（比如 C 的位置），保证一条简单几何规则总能给出可行路。

### 4.3 建议的分阶段落地
- **阶段 1**：写 `plan_cable_routing_arc_spline`（新函数，与现有并列，`routing.route_mode: arc_spline` 开关）。先只保证**绳子拓扑对**（相切圆弧拼接 + 绕向匹配 signature），在当前布局上跑通。
- **阶段 2**：加**机械臂净空**处理。先用启发式（弧向偏"低/朝底座"），用改进的 3D 前臂代理或真实 collision 自检验证；不行再退化到"压低/加宽"。
- **阶段 3**：等 `cable_routing_generator` 接入 seed 随机布局后，**跨多个 seed** 验证批量鲁棒性（这才是真正检验"适合批量生成"的地方）。
- **保留退路**：`smooth_route:false` 的手写点 + Catmull-Rom 平滑，作为**固定布局**下的可用基线。

---

## 5. 优先级判断

- cable_routing 目前是**确定性单布局**，手写+平滑这版**够用**（当前 video 可保留）。
- 相切圆弧生成器的价值在**加入 seed 变式布局之后**才真正兑现。所以它的优先级应该和"给 cable_routing 接入 seed 随机化"绑在一起推进——单独现在就做圆弧生成器、却还没有变布局来检验，收益有限。
- 建议顺序：先确认这版平滑手写路径在当前布局能物理跑通（GPU 复测）→ 再决定是立刻上圆弧生成器，还是等 seed 随机化一起做。

---

## 6. 一句话总结

当前"平滑手写路径"只适合**当前这一个固定布局**，**不适合批量生成**（它没有生成能力，只是抹平了人工调好的路）。要批量，就得走用户说的**相切圆弧拼接**这类**布局自适应生成器**——但必须把**机械臂本体体积/可行性**当成一等约束显式处理，否则会重演"前臂横扫 P2"。
