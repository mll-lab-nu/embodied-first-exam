## 3. 先固定统一合同（W0）

以下是拟新增或统一的合同，字段名在实现评审时最终冻结；并非当前已有接口。

| 对象 | 拟统一的语义 | 兼容要求 |
| --- | --- | --- |
| 请求记录 | 请求 ID、输入、是否接受、拒绝原因；请求不等于执行 | 保留诊断能力，不把拒绝行塞进可回放 `actions` |
| 执行轨迹 | 仅已提交执行行；每行实际 tick 数、起止模拟时间、有效控制目标、终态原因 | 版本化格式；统一读取器处理旧 NPZ 和旧 `live_rows`，不猜测缺失的实际 tick 数 |
| 执行时钟 | 从 Env/world 汇总实际完成的 tick；明确控制周期、物理 tick、solver substep 三层 | 禁止用动作行数乘固定周期代替实际时间 |
| 评测状态 | solved / unsolved / invalid_submission / not_evaluable / infra_failed 的原因和队列策略 | 沿用收集器外部状态映射；Harbor reward 中保持数值字段，字符串诊断放结构化结果 |
| 权威评分记录 | 输入身份、评分版本、所需 replay 的结果、最终 verdict、提交 ID | `reward.json/txt` 是可恢复的兼容输出；不能成为互相冲突的两份权威状态 |
| 媒体记录 | pending / complete / error、覆盖时间、相机、文件哈希 | 媒体失败可使输出不完整，但不能推翻已经持久化的有效评分 |
| 身份 | 源码、运行镜像 digest、工具包、client、实例资产、初态 profile、协议与 terminal 版本 | 新 run 固定全套身份；预检过期时重新预检，不能跨版本直接 resume |

评分和队列策略需要一起冻结：非法 agent 提交记录为失败的有效尝试并继续下一任务；实例不兼容在预检阻止受影响任务进入运行，不计入有效求解分母；基础设施故障保留现有停止/受控恢复策略。HF 导出同时提供 attempted、valid、invalid、not_evaluable、infra 计数及分母定义，不通过修改分类掩盖故障。

轨迹格式更新不等于允许 agent 任意缩短控制周期。每行实际 tick 数由可信运行端产生；privileged 外部输入仍遵守控制周期约束，不能靠自行填写元数据改变物理时间。旧数据只能按其已记录的能力回放，并显式标注时间精度。

## 4. 每项修复的实现与验收

### W1：B04，将提交解析与物理评分分开

在创建 Session 前完成 NPZ 容器、`actions`、维度、长度、dtype、有限值及控制输入检查。将已识别的提交格式错误映射为 `invalid_submission`，输出数值 reward 与可诊断原因。随后单独进入实例加载和物理评分阶段。

错误分类依据阶段与明确异常类型：损坏的 agent 文件可归提交错误，宿主读盘失败、运行资产损坏、物理初始化失败仍归基础设施或实例故障。不能把所有 `ValueError` 或全部异常都归 agent 错误。

验收：缺键、损坏 ZIP、错误 dtype/shape、NaN/Inf、空或超限轨迹均有明确结果；非法提交不创建模拟器；编排继续下一任务。另注入初始化失败与宿主 I/O 故障，确认仍按 infra 策略停止或恢复。测试贯穿 grader → collector → difficulty，而不只断言一个异常类型。

### W2：B07，严格执行整数控制周期

在共享请求入口统一校验 `dt` 有限、处于允许范围，且为控制周期的整数倍；使用明确的浮点容差，不使用精确相等，也不默默四舍五入。校验通过后转成整数周期数，后续插值、chunk 上限和步数均使用该整数。

验收：40 Hz 下 `dt=0.0375` 在动作执行和 journal 写入前拒绝；合法周期以及其合理浮点表示误差通过；边界、两种插值方式和 chunk 限额共用规则。视频 fps 不参与控制周期校验。

### W3：B06，统一实际执行轨迹和时钟

主要入口为 [Session](../../harbor_templates/topogym/common/rcb_topogym.py)、[Env](../../topogym/simulator/env.py)、[standard server](../../harbor_templates/topogym/limited/environment/sim/server.py) 与 [replay](../../harbor_templates/topogym/limited/environment/sim/replay.py)。

1. 验证、裁剪、native hold 目标解释及 command 接受完成后，才进入执行阶段；拒绝动作只留请求诊断。保留合并后的 native target 行为，不重新从公开夹爪宽度反推 hold。
2. 执行后消费 Env 的实际 `physics_steps`、`action_duration_s` 和有效目标，提交执行记录。终态后的请求返回明确状态，不增加执行行、控制步或物理时间。
3. 导出的 canonical `actions` 只包含执行前缀；原请求及未执行尾部另作诊断。正式 replay、通用 replay、收集器和 HF 使用同一个轨迹读取器。
4. 对控制周期内提前结束，记录实际 tick 数；可信回放支持该行的执行上限，继续逐 tick 检查终态。回放若更早结束或状态不一致，报告差异，不能为了匹配行数强制越过终态。
5. journal 区分执行意图与已提交结果。物理已推进、提交记录尚未落盘的崩溃窗口标为不确定；隔离旧进程，从已提交前缀按现有 approximate-resume 合同恢复。不得宣称原生崩溃下实现物理 exactly-once。

验收：拒绝动作对应 0 执行行；终态后继续调用不增加记录；5 行请求、1 行执行时，所有正式消费者只回放 1 行；提前结束于 3 tick 时，上报 `3 / 0.0075 s`，不再变成 `10 / 0.025 s`。在 command 前、部分物理推进后、journal 提交前后注入故障，验证提交边界和恢复状态。

### W4：B08，两模式采用相同的实例资格检查

复用现有初态身份和 Blanket v2 兼容机制，统一 privileged/standard 的执行前资格检查。仅把 privileged 的 `strict` 改为 True 不足以关闭问题：当前软体 centroid 比较不能识别等质心的形变。

检查分为两层：不可变身份核对 task、资产/拓扑、冻结初态、相关物理配置及工具身份；恢复状态按任务后端核对有稳定对应关系的位姿、节点位置/速度等，使用经过实测的容差。四元数正负等价不得误判；不同 GPU profile 只能使用已经取得资格的兼容路径，不能要求所有 GPU 浮点字节完全一致，也不能默认跨 GPU 都兼容。

验收：同质心但节点形状改变、错误资产/seed、错误初态布局被拒绝；允许范围内数值差异和四元数等价通过。两个模式都在 agent 动作前返回 `not_evaluable`/实例不匹配诊断；注入 `instance_matches=False` 后，即使模拟 replay 返回成功也不能得到 `success=1`。

### W5：B05，评分先持久化，媒体独立收尾

保留正常两遍流程：privileged 两次评分回放，第二遍录制；standard live 后退出服务，再独立 replay 并录制。无需增加固定第三遍。

所有必需评分结果齐备后，先保存权威评分记录，再关闭编码和验证媒体。使用同目录临时文件、文件同步、原子替换及必要的目录同步；由提交 ID 保证兼容 reward 输出与权威记录一致。多文件写入本身不具备整体原子性，恢复逻辑必须能从已提交权威记录补齐 `reward.json/txt`。

standard replay 将结果落盘，finalize 从该记录读取，不只依赖 replay 进程最后一次 stdout JSON；启动进程或监督方发现媒体进程退出时仍能收集已提交成绩。`finalized` 不能在评分提交前提前标真。

验收：普通编码异常、子进程退出和受控 SIGKILL 分别在评分提交前后注入。提交后两次成功的 verdict 保留且可补齐 reward；提交前无完整证据时只能报告 incomplete/infra。诊断中保留媒体错误，不将其改成 unsolved，也不能承诺抢救尚未写入磁盘的内存结果。

### W6：B09，迁移共享录制并校正时间轴

实施时核对发现，当前 [topogym.recording](../../topogym/recording/README.md) 的接口是 `RecordingSession`，旧 `prepare/session/validate/archive` 函数已不适用。按实际 `append/append_final → finish/close` 生命周期接入并使用共享解码校验，由 Env 提供真实 SensorFrame。保留冻结物理、机器人、任务和观测配置，不另建 writer，不通过补物理步获得录像帧。

必须 reset 到本次回放初态后才开始采集；按真实物理时间调度视频采样，保证初态和末态都有对应画面。`last.png` 从最终状态取帧；多相机与 proprio 标记相同物理 tick。非整数频率比采用共享时间轴，记录物理时间和呈现时间，CFR 量化误差上限明示为一个输出帧周期，不要求不可能的逐帧绝对等时。

软体的离线重渲染必须有完整可恢复状态，不能用刚体位姿适配器冒充节点状态。正式视频沿用 Nyx + compact_lab；无视觉资源时明确记录失败。

验收：0、1、2、5 个控制步、控制周期内终止、40 Hz→15 fps、reset 后再录制、编码故障均覆盖。5 步案例不得出现上一轮终态开头，末帧必须来自 action_5 或更早的真实终态；完整解码、多视角同步、时间轴检查通过，且录像开关不改变动作/物理计数。

### W7：B11，统一服务预算、客户端时限与恢复语义

由共享协议定义各 endpoint 的预算，客户端等待时间覆盖服务预算与传输余量；排队时间计入请求期限，在首次物理执行前检查是否过期。每个已完成控制步检查断连、期限并保存进度，明确返回最后提交执行位置。

新请求使用 operation ID；超时后先查询该操作状态，重试相同 ID 不重复执行。client、server、journal 的 ID 和恢复规则同步升级；旧协议客户端通过显式兼容模式工作，不静默混用新语义。

GPU 原生调用不能靠 Python 线程安全抢占。长时间没有进度时由拥有该进程的 watchdog 终止、标记 infra 并保留恢复材料；终止前后的执行不确定性遵守 W3。请求软期限的超出范围取决于最长不可抢占片段，不能承诺所有物理调用都在固定毫秒内取消。

验收：用可控时钟测试 observe/submit、排队超时、断连、慢控制步、重复 operation ID 和恢复；客户端超时后不盲目重复提交。真实 GPU watchdog 测试只终止测试拥有的进程，已提交 journal 可读取。

### W8：B12，不完整 prepare 使用独立 attempt 恢复

将“目录存在”改为“完整准备事务已提交”：独立 attempt 目录写入资产，校验文件、哈希、权限、profile/实例兼容后，原子发布完成 manifest 或指针。引用该 attempt 的任务生成只能发生在提交之后。

resume 检测到不完整目录时保留其日志和残留，创建有编号的新 attempt；加入同实例锁、有限重试次数及失败原因。成功冻结包引用的目录不搬移、不覆盖。缓存命中必须满足完整身份，不能复用错误 seed 或 GPU profile 的文件。

验收：分别在创建目录、写状态、写 manifest、发布完成标记前后中断，恢复后能完成且不破坏旧证据；重复 resume 幂等；并发 prepare 不混写；损坏的“完成”目录不能被当作有效缓存；非 root 可读性继续通过。

### W9：B13，容器清理限定所有权

将 local 兼容分支的 run_id 单标签过滤改为 workspace 身份、run_id、owner/run token 联合约束，并优先记录本次实际创建的 container ID。复用 delivery 的归属思路，统一创建与清理逻辑；删除前 inspect 复核，身份不确定时停止删除并记录原因。

没有新归属标签的旧容器不自动纳入宽泛清理，也不以 GPU lock 代替 workspace 归属。此项不使用全局 prune，不删除镜像层、构建缓存或其他任务证据。

验收：两个 workspace 使用相同 run_id，清理一个仅影响其拥有的容器；不同 owner、无归属标签、已停止的无关容器均保留。先以 Docker API 替身验证筛选和竞态，再用本次创建的小型容器验证真实清理，无需启动 GPU。

### W10：B10，补齐子步观测后发布判据新版本

当前例子中一个控制周期为 10 个物理 tick，每 tick 内还有 solver substep；具体参数以冻结配置为准。刚体任务使用 tick 末 contacts，不能证明子步内从未出现禁止接触。该缺口不能仅靠多跑现有末态测试关闭。

第一步做诊断：扩展 [rigid contact collector](../../topogym/world/physics/rigid_contacts.py) 的事件汇总，记录接触对象角色、深度、tick/substep 和当时的抓持豁免状态；每 tick/reset 清楚划分生命周期，保持事件存储有界。审查 Coil、Keyhole、Hedgehog、Horseshoe、Claws 的消费路径，并对已有 Buzz/Fiber 子步采集做回归。

第二步发布显式 `terminal_contract_version`。建议新合同规定“任一已覆盖 solver substep 出现达到现有任务阈值的禁止接触，均计入 failure”，保留现有阈值及抓持豁免含义。历史合同和历史成绩不改变；新增规则改变成功率时必须独立解释。

对各后端列能力表：刚体可采集什么、IPC/FEM 是否提供足够事件。缺少事件不能解释为无违规；需要新合同却缺少覆盖能力时标记未具备评测资格。子步接触覆盖也不等于数学意义的连续碰撞检测，更不自动覆盖穿环等所有几何过程事件。

验收：合成事件覆盖“前子步越阈值、末子步恢复”、合法接触、阈值边界、抓持豁免时序、reset/replay 清空；随后用真实 GPU 场景复现短暂禁止接触与合法对照。未获真实事件证据的任务/后端保持 pending，不能用 CPU 替身直接关闭。

## 5. 性能工作项：先建立分段基线

这些工作与正确性修复分开记账。优化不能修改物理阈值、终态合同或用更少物理步制造加速；正确性修复导致必要开销时单独说明。

| 方向 | 测量与候选修改 | 验收边界 |
| --- | --- | --- |
| O01 Knot | 拆分首次 reset、判据、控制和回放耗时；考虑将已验证向量化下沉到共享几何实现，使首次 reset 和纯 Env 受益 | 保留随机、交叉、退化输入的等价验证；测 O(N²) 内存，不能把函数约 96 倍当整局加速 |
| O02 Blanket | profile 投影并集，比较拓扑不变部分缓存、批处理等方案 | 当前 15,842 三角形约 0.2168 s/次仅为单次 CPU 基线；不以凸包近似替换真实覆盖率，验证临界判据一致 |
| O03 RGB/视频 | 无视频评分关闭非必要帧获取和 stack；agent 需要 RGB 的阶段保留观测 | 区分无媒体与无 RGB；物理、终态和需要的观测一致，比较峰值内存与墙钟 |
| O04 历史和设备同步 | 分离 world 状态读取、CPU/GPU 同步、Task/RNG 复制、checkpoint 时间及内存 | 不削弱公开 rewind、每 tick 历史和 RNG 恢复；总 VRAM、Torch 分配和缓存分别报告 |
| O05 prepare/初始化 | 对资产准备、建场景、settle、reset、状态导出分别计时；重点定位 Rope 超过 300 s 的初始化 | 先取得对照再归因；资格/身份匹配才复用缓存，agent 可写缓存不能直接进入可信 verifier |
| O06 镜像 | 测 prepare image 的上下文打包、依赖层、编译层、运行层及拉取；优化失效范围和重复复制 | 保留现有 BuildKit 缓存，不清缓存换取演示；分别报告冷构建、缓存命中构建、仅源码变更构建 |

测量使用固定硬件、源码、seed、实例、模式、视频设置和成功/失败轨迹；记录墙钟、实际模拟时间、real-time factor、RSS/VRAM 峰值、样本数。短基准重复采样，报告中位数与范围；样本不足不发布有误导性的 p95。冷构建成本高，可先报告一次分段实测及其限制。

功能修复前后使用相同工作量比较；性能 PR 给出实际收益、回归及额外内存，不预设未经测量的“整体加速多少倍”。FEM checkpoint 的短前缀证据不足以关闭长期显存项，必须补长程与多次 reset 测量。

## 6. 分层验收与可关闭条件

所有新证据保存到独立 `runs/test_results/run_trials_post_merge_repair_<run_id>/`，包含源码/资产身份、命令、退出码、原始日志、断言、资源采样和状态矩阵。不得覆盖审查或合并验证的原始材料。

| 层级 | 必须执行的内容 | 通过后允许声称 |
| --- | --- | --- |
| G0：CPU 合同 | 保留原 160 项回归与 14 项协议基线，加入 W1–W9 的边界/故障注入及 W10 事件替身测试；检查生成工具身份和协议副本一致 | 对应逻辑与协议通过，不证明真实物理或任务成功 |
| G1：真实产物链 | 新生成 privileged/standard 包，在容器非 root 环境验证输入分类、verdict 恢复、collector 与 HF 离线导出；真实受控进程中断与媒体解码 | 生成/运行/收集使用同一合同；具体无 GPU 案例仍标明替身 |
| G2：代表性 GPU | 单臂与双臂刚体、Blanket 三档恢复/接续、四类 IPC、标准 live→fresh replay；比较实际 tick、终态和输出；补 Knot 长程、Rope 初始化 | 实测后端和实例通过，其他项不得外推 |
| G3：完整流程矩阵 | 13 tasks × 3 难度 × 2 模式 = 78 项，固定 sample；覆盖 prepare、预检、执行、terminal/限时收尾、grading、视频和结果导出 | 当前 cu128 发布的全矩阵生命周期状态明确 |
| G4：正负评分与新判据 | 对当前身份已验证的参考轨迹做至少一个完整成功、明确失败及提前终态案例；W10 另补真实子步违规/合法对照及受影响任务覆盖 | 只对实测实例给出 solved/判据有效结论 |

G3 的短程生命周期全部通过不代表 39 个实例全部可解；完整求解证据另列。没有参考解的任务不能填“成功判据已验证”。cu130 不继承 cu128 的 GPU 资格，未跑则明确未验收。

新版本面向完整支持矩阵发布时，必需行不得靠跳过来获得全绿。若某后端尚未通过，可发布明确缩小支持范围的候选版并阻止未合格任务进入正式队列，保留 pending，而不是宣称所有问题已修复。

检查顺序为 CPU → 小规模容器 → 代表性 GPU → 全矩阵，避免先花费整批模型评测成本。GPU 按资源可用性串行安排，监控 CPU/内存；遵守仓库规则，内存达到 90% 时只停止本次拥有的负载。当前暂停的长跑不会因本文自动恢复。

每个 B 编号仅在“修改 + 原复现转为回归 + 对应真实环境验收 + 文档/包身份更新”齐备后关闭；标记 CPU-only、GPU pending 或 contract pending 时均视为尚未完整关闭。

## 7. 镜像、工具与结果发布（W11）

1. **先冻结实现与 schema，再生成发布候选。** 根据实际变更升级工具、共享协议、运行镜像及结果 schema；具体版本号在发布时分配。不能认为只换 `0.2.5` 镜像就获得任务工具修复，也不能在旧 tag 下覆盖内容。
2. 从候选源码生成全新包，固定 runtime image digest、包内工具和 client 身份，更新预检 identity。核对新 run-trials 的 prepare、run、grading、收集及 `--results_to_hf` 离线导出引用同一发布集合；入口参数以实际 CLI 为准。
3. 历史包仍按其冻结身份运行。新旧 NPZ、模式后缀、结果 schema 兼容在读取层处理；显式迁移产生新的包/产物身份，不原地替换历史证据。
4. 先完成 G0–G2，再完成声明支持范围的 G3/G4。保存每项通过、失败、未验证、基础设施故障及原因；不能只提交一份总体“passed”。
5. 发布文档同步说明实际执行轨迹、dt、实例资格、媒体状态、请求恢复和 B10 合同；更新 RCB 手册、协议说明、生成器说明及 HF 字段解释。
6. 回滚按发布身份切回上一版本，停止的仅是本次拥有的任务。新 schema 的 run 不直接用旧 runtime resume；保留 attempt、journal、verdict 和媒体证据，再用新的 run ID 重新运行。
