## Task
MuJoCo Playground `Go1JoystickFlatTerrain` (Unitree Go1) on the same frozen instance as `mujoco_playground_go1_joystick_flat_terrain-privileged`: Make the Unitree Go1 follow the joystick command schedule on flat ground for the whole 20 s episode without falling over.
For 20 s the robot gets a joystick command schedule (4 segments: planar velocity and yaw rate in its own frame) and must track it without falling over. Standard mode (eai-standard/2.2): the agent drives the robot through a client, with 10 resets (only
the last episode is graded), the robot's own sensors and the cameras that follow it.

## Difficulty
Same instance and success check as `mujoco_playground_go1_joystick_flat_terrain-privileged`. In standard mode the agent loses free resets, the simulator and
the world state: it sees camera images and proprioception (joints, IMU, foot contacts), acts in joint position chunks,
and gets 10 resets (`RCB_RESET_BUDGET`, the compose file's default; PROTOCOL §4.5), so it has to close the loop
on the robot's own sensors; only the last episode is graded.

## Reference solution
`solution/oracle_replay.py` streams the privileged reference's rows (`solution/oracle.npy`, 1000 rows, float32-exact)
through the client in `hold` chunks; it uses no privileged information at run time. The service's recorded trajectory
is then exactly the privileged reference, and the episode ends after the 1000 steps of the schedule, with success.

## Verification
The verdict is the live episode's (`graded_by = "live"`, `replays = 0`): the sim service runs the task's check on the
episode it ran and records every executed control step. The collect hook (`environment/sim/finalize.sh`) ends the
service, writes that verdict into `final.json` (nothing is replayed to grade it), then renders `replay.mp4` from the
recorded trajectory in one video-only pass (`environment/sim/video.py`), which never changes the verdict;
`tests/grade.py` (separate sandbox, no network) passes iff the live check succeeded. The service checks the frozen
instance when it builds the scene: a start state that does not hash to the instance's `state_sha` gets no episode
(`instance_mismatch`, `infra_error = 1`). Oracle: success, worst segment errors 0.073 m/s and 0.091 rad/s.

### Change Log
- 2026-10-10 (review 0067): a `final.json` that is missing, unreadable or was never finalized by the collect hook is graded `infra_error = 1` (no verdict on the agent); before, a missing one was a plain 0 and an unfinalized one was graded as it stood. The collect hook writes `final.json` atomically. A request field of the wrong type (`dt` or `seconds` null, `cameras` not a list of names, a `note` that is not a string) is answered 400 before any physics instead of ending the episode with a 500. `meta["time_left_s"]` counts from the agent's first call, not from the service's start.
- 2026-10-10 (review round 2, board 0067): the client only (`environment/rcb_client.py`). `Robot()` waits up to 3600 s for the service (was 600 s) and prints its progress to stderr once a minute, so the first `Robot()` outlasts the simulator's start (no effect on this benchmark, whose service is up within a minute); `cameras="name"` (a string) is one camera, no longer its characters. The service, the collect hook, the grader, the scene and the pass rule are unchanged.
- 2026-10-10 (review round 3, board 0067): the shared service layer and the client only (`environment/sim/rcb_limited.py`, `environment/rcb_client.py`). A camera named more than once in `cameras` is rendered and returned once (N copies of one name made the service build N x N images within the frame budget, which could exhaust its memory). A service that has given up on the episode (it could not start it, or could not resume it after its crashes) answers every request with 409 and the reason, and `Robot()` / `wait_ready()` raise `EpisodeOver` at once; before, nothing answered and they waited out their timeout (up to an hour). The adapter, the collect hook, the grader, the scene and the pass rule are unchanged.
- 2026-10-14 (owner decision C1, board 0113): 10 resets (PROTOCOL §4.5). The service (`environment/sim/server.py`) gained the optional reset capability: `RCB_RESET_BUDGET` (the compose file's default 10; 0 restores the old single episode), `POST /reset` abandons the running or ended episode and starts a new one from the same frozen start (no physics), refused (409) after a success, once the agent's time is up and once the budget is spent; only the last episode is graded (`trajectory.npz` holds its rows, replayed twice from the frozen start as before); `/status` and every `meta` add `episode`, `resets_left` and `control_steps_total`; `final.json` and `reward.json` add `resets`, `reset_budget` and `episodes`. A crash resumes the current episode (the journal is replayed with the committed resets). The instruction's rules, the client example (`POST /reset` through `Robot._post`) and this README say so. The scene, the instance, the success check and the grader's pass rule are unchanged; results recorded before this change ran with one episode and are reported separately.
- 2026-10-17 (owner, boards 0150 and 0151): **graded by the live episode, no grading replay.** `environment/sim/finalize.sh`, `environment/sim/server.py`, the new `environment/sim/video.py`, `tests/grade.py`, `task.toml`, the compose file. Success is the task's check on the episode the service ran (`graded_by = "live"`, `replays = 0`): `rcb_quadruped.Session.check()` on the live simulator when the episode ends, with its holds inside it. The collect hook no longer replays the trajectory in two fresh processes (success was live ∧ both replays ∧ the same final state); the rule is the same, since the replays ran the same rows through the same check. `replay.mp4` comes from one video-only pass after the verdict. A new collect hook on `main` (`kill -9 -1`, before the sim's) stops whatever the agent left running before the episode is ended and judged (PROTOCOL H.4). The frozen instance is checked when the service builds the scene (its `state_sha`; a mismatch gets no episode, `instance_mismatch`, infrastructure; before, the tooling raised and the service restarted until compose gave up). The scene, the instance, the pass rule and what the agent sees are unchanged, so the task keeps its name; `reward.json` no longer has `replay_success`, `deterministic` and `live_matches_replay`.
