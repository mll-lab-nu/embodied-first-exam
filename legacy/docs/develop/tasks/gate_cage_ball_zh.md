## 1. 任务回顾（术语按仓库）

球从入口段（`channel.entry_start_y` 到 `channel.door_y`）匀速滚进封闭区（`door_y` 到 `channel.flat_end_y`），撞远端墙后原速滚回。
机器人从停放架（`gate_rack`）取闸板，搬到门口导柱槽（`gate_slot`）上方悬停，等球进门后把闸板插下，把球关在封闭区里。
球一开始就是自由的，机械臂在和它赛跑。

| 量 | 来源 | 现值 |
|---|---|---|
| `entry_delay` = (`door_y` − `release_y`) / `speed` | `GateCageBallLayout.entry_delay()` | 3.33 s |
| 窗口 `window` = 2·(`flat_end_y` − 球半径 − `door_y`) / `speed` | `predicted_window()` | 2.00 s |
| `t_ready`：臂拿着闸板在门口悬停就位 | `motion.*` 步数 × `timing.sim_dt`（= `GatedInsertPrimitive.time_to_station`） | 2.40 s |
| `insert_duration`：从下板到落座 | 同上（= `insert_duration`） | 1.30 s |

触发规则（`topogym/planning/gate_cage_ball_planner.py`，`run.trigger`）：

| 规则 | 行为 | 预期 |
|---|---|---|
| `oracle` | 球在门内且「回到门口的时间 − `insert_duration`」≥ `timing.safety_margin` 才下板 | 成功 |
| `greedy` | 到位就插，不看球 | 臂先到（`hover_wait` > 0）失败，球先到可能侥幸 |
| `fixed_delay` | 开始后 `run.fixed_delay_s` 秒就插，不看球（2026-09-03 新增） | 起点与球速逐 seed 变后落到中间；「不感知」策略的上限 |

## 2. 可解性判据与 `timing:` 段

- 判据 A：`window` ≥ `insert_duration` + `safety_margin`（球进来后封得住）。
- 判据 B：`entry_delay` + `window` − `insert_duration` ≥ `t_ready` + `ready_margin`（臂就位时最晚下板时刻还没过）。

两条判据把球的时间量和机械臂的时间量放在一起比。机械臂的时间量是步数乘步长，步长本来只在 env 配置（`env.sim.dt`），
触发规则的富余本来只在 run 配置；而 yaml `variation:` 块引用的 `validate_task_cfg(task_cfg)` / `derive_task_cfg(task_cfg)`
只拿得到 `cfg.task`。所以 task yaml 加了 `timing:` 段：`sim_dt` 0.01、`safety_margin` 0.15（从 run 配置搬来）、`ready_margin` 0.10（新）。
demo 建场景时断言 `timing.sim_dt == env.sim.dt`，并断言 Layout 的 `t_ready()` / `insert_duration()` 与原语的同名公式相等。

`entry_delay − t_ready`（`hover_wait`）的正负只报告不约束：它是三条触发规则拉开差距的机制，按它调几何等于把基线分数写进场景定义
（`configs/run_configs/gate_cage_ball_gate.yaml` 尾注）。

## 3. 变体轴与派生

| 类 | 叶子 | 抽法 | 说明 |
|---|---|---|---|

| B | `ball.speed` | U[0.05, 0.10] | 同时缩放 `entry_delay` 与窗口。2026-09-08 从 [0.08, 0.16] 放慢一档 |
| B | `channel.center_x` | U[0.055, 0.095] | 轨道左右平移 |

| B→C | `channel.flat_end_frac` → `channel.flat_end_y` | **派生** | `[max(flat_end_y_min 0.11, 判据 A 取等), flat_end_y_max 0.20]`；球速越快下界越长 |

visual 10/10 有帧且逐 seed 可分；oracle **6/10**，四格失败标签 `ball_pinched_in_doorway`（seed 5/6/7/8），

判定时刻球恰好在门口附近往返，就被标成夹住。这是判据的定义错误，不是行为错误；默认实例没暴露只是窗口相位凑巧。
改为：`pinched` = 闸板挡着 **且** 闸板被顶住没坐到位（`gate_bottom_z` > `gate.seated_bottom_z` + 5 mm）**且** 球体在板的 y 跨度内。
只有「板压在球上」才算夹住。

### 5.3 角点 sweep 暴露的取板原语缺陷（2026-09-03，`runs/gate_cage_ball_corners/`）

`tests/check_variant_corners.py` 把包络 6 条轴的端点全组合成 64 个角点，`variant_corners_sweep.sh` 逐格送进物理（固定布局路径，不碰随机化）。
09-02 晚首跑 oracle **54/64**：10 个失败格全在停放架 `center_y=−0.03` 且 `x_frac=0`（架在 x_min −0.120）那一角，8 格 `grasp_check_failed`
（`plate_yaw` 2.19° > 2.0°，`finger_qpos` −0.0010）、2 格时序（c002 `pinched`、c034 `ball_outside`，`slack` 0.10 s）。

**根因（逐步追踪 + 对照实验）。** approach 是从 home（指开合轴沿 x）30 步移到停放架上方 `approach_z`，同时姿态要转到 `default_ee_quat`
（指开合轴沿 y），腕转 90°。`GatedInsertPrimitive._move` 收了 `start_quat` 却没用，每一步给 IK 的姿态目标都是终态；派生源
`AxialInsertPrimitive._move_linear` 和 `PivotLeverPrimitive._move` 都用 `_quat_slerp` 把姿态沿同一条余弦曲线插值，08-17 派生时没抄。
IK 面对 90° 的姿态误差给出的中间解让手下沉、倾斜。同一段移动（home → 停放架上方）的对照：

| 做法 | 下沉 | 倾角 | 水平落后 |
|---|---|---|---|
| 只平移，腕不转 | 1.5 mm | 1.7° | 61 mm |
| 平移 + 每步姿态目标为终态（原写法） | 63 mm | 17° | 56 mm |
| 只原地转腕，不平移 | 70 mm | 18° | 40 mm |
| 原写法放慢 4 倍（120 步） | 70 mm | 18° | 39 mm |
| 平移 + 姿态插值（修后） | 1.5 mm | 1.6° | 60 mm |

放慢不消下沉，说明是解序列本身而非动态滞后；水平落后 40 mm 是 165 mm 平移压在 0.3 s 里的独立现象，settle 30 步归零，
不是撞板原因（且加 settle 会把 `t_ready` 2.40 → 2.70 s、改变 `release_y` 派生上界，本次不加）。
`approach_z` 0.240 给指尖的静态净空只有 12 mm（指垫 32 mm），下沉 60 mm 后指尖从板顶边缘扫过：第 12 步起两根耦合的手指被顶着合拢到
−0.001，板被推向 −x 14 mm、偏摆 2.1°；随后合爪、attachment 把已偏的板挂上手。腕单向转，转到一半两指都甩到手的 −y 侧，板在 −y 侧
（`center_y=−0.03`）时正好套住一根手指；在 +y 侧时从板面旁边过，不碰。架越靠 x_min 路径越长，最低点越深入板端。
可达性无关：底座到架 0.451 m，`lift_test` 时手到位 ±4 mm。

被碰的其实是 16 格：另 8 格板被推 69 mm、偏摆只 1.76°，判「过」，全程手指空夹（`finger_qpos` 0.0018）、靠 attachment 拎着插进槽——
`min_finger_qpos` 为 null 漏掉的假成功。

**处置（oracle 侧，包络不动）：** ① `_move` 补 `_quat_slerp`（对齐派生源）；② `min_finger_qpos` null → 0.004（夹到板 0.0063–0.0075，
空夹 ≤ 0.0018）；③ `checks()` 加 `approach_clearance ≥ 0.030`（不随任何轴变，现值 0.032，防以后改低 `approach_z`）；
④ `check_gate_cage_ball_geometry.py` 加 `approach_z=0.220` 必须被 `validate()` 拒绝。不把「板不能在扫掠体积里」写进包络：那是固化 bug 的形状。

### 6.2 「加长」本身抬不高观察时间的下限

球在画面里滚多久 = (门 y − 出生 y) / 球速，而出生位置由 `release_frac` 在**整条可出生段**上抽。可出生段的近门那一端是 `door_y − 球半径 − spawn_door_margin`，`spawn_door_margin` 原本只有 2 cm、意思是「整球在门外」。所以加长引道只把观察时间的**范围**拉开（1000 seed 实测 0.53–10.13 s），下限还是 0.53 s——最慢和最快差 20 倍，而最快的那些格与改动前没有区别。

把 `spawn_door_margin` 从 2 cm 提到 8 cm，下限抬到 **1.21 s**、中位 4.33 s。代价是「球先到」的实例比例从 27.5% 降到 18%：

| 出生门余量 | 观察时间 最小 / 中位 / 最大 | 球先到 | 臂先到 |
|---|---|---|---|
| 2 cm（改前） | 0.53 / 4.06 / 10.13 s | 110 / 400 | 290 / 400 |
| **8 cm（取值）** | **1.21 / 4.33 / 10.13 s** | **72 / 400** | 328 / 400 |
| 12 cm | 1.67 / 4.54 / 10.13 s | 39 / 400 | 361 / 400 |
| 16 cm | 2.07 / 4.80 / 10.13 s | 18 / 400 | 382 / 400 |

**为什么不取更大的**：`hover_wait`（球到门时刻 − 臂就位时刻）的正负是三条触发规则拉开差距的机制，任务文档写明它「只报告不约束，为别的目的把它调掉等于把基线分数写进场景」。16 cm 时球先到只剩 4.5%，那条机制就名存实亡了。8 cm 是两者都还成立的位置。

### 6.3 球径的难度不在窗口上

窗口 = 2 × (封闭区长 − 球半径) / 球速。封闭区 11–20 cm，而球半径才 2.4–3.6 cm，所以球径只让窗口从 2.10 s 变到 1.90 s——**10% 的差，当不了难度轴**。

真正随球径变的是**「不能下板」的那一段**。判定器把「板压在球身上」写成

```
under_plate = |球 y − 板 y| < 球半径 + 半个板厚      （gate_cage_ball_verifier.py 的 classify）
```

所以门口那条禁区的宽度直接随球径放大：±3.0 / ±3.6 / ±4.2 cm。按球速折成时间，球每经过门口一趟就有这么久不能下板——1000 seed 实测跨度 **0.60–1.68 s**（球径 × 球速的联合效果，2.8 倍）。球越大越难，机制在这里。

**因此槽道、闸板、导柱一概不动。** 三档球径下：每侧净空 2.1 / 1.5 / 0.9 cm、侧壁高出球顶 4.2 / 3.0 / 1.8 cm、入口壁高出球心 2.1 / 1.5 / 0.9 cm，都成立（`ball_fits_channel` 与 `wall_contains_ball` 两行守住）。驱动器每步把横向速度写成 0（`_ball_drive` 的 `velocity[0] = 0.0`），每侧净空不进入动力学，只是画面上球更贴壁或更松。闸板落底时板底离槽底 1.2 cm，最小的球直径 4.8 cm 也过不去，封门仍靠几何。

**反过来让槽道跟着球径缩放要付的价**（算过，留档）：内净宽、侧壁高、入口壁高、闸板宽、板顶 z 五个量要派生，板高 8.4 → 10.8 cm、**板质量 0.896 → 1.395 kg（±23%）**、取板时指垫的高度移动 ±1 cm，插入原语与取板高度都要重标定，导柱 13.5 cm 还压不住 12.0 cm 的板顶。换来的窗口差只有 10%——不值。

### 6.4 悬停上限从「碰巧够」变成一行判据

臂就位之后要等球，等待时长 = `hover_wait`。改前最长 0.93 s，上限 900 步 = 9 s，余量大到没人会想起它。改后引道 55 cm、球速最慢 0.050，`hover_wait` 最长到 **7.80 s**（1000 seed 实测），9 s 只剩 1.2 s——一旦包络再动一点就会撞上 `trigger_never_fired`，而那是个执行侧的失败标签，会被误读成规则的问题。

处置：上限 900 → 1300 步，并加 `hover_within_cap` 一行进 `checks()`。这是本轮第三处同形的事（另两处：cloth_unpleat 的斜置经过 `spread_span`、球径经过 `under_plate`）——**一条轴看起来免费，往往是因为没查它经过哪些既有读数**。

### 6.5 固定延时对照要重标，而且它的上限本来就该掉下来

`fixed_delay` 从 episode 开始数够固定秒数就下板，是「时机能不能靠背一个数」的对照。改前 3.6 s ≈ 默认实例上 oracle 的下板时刻，实测 6/10。

改后球到门的时刻变成 1.15–10.20 s（中位 4.24），3.6 s 会几乎总是早于球到达，这条对照退化成恒 0。重标到 **5.5 s**：1000 seed 上落在「可下板窗口」内 372 次，是最优取值。

| 固定延时 | 落在窗口内 |
|---|---|
| 4.0 s | 297 / 1000 |
| 4.5 s | 349 / 1000 |
| **5.5 s** | **372 / 1000** |
| 6.0 s | 338 / 1000 |

**任何固定延时的上限只有约 37%**（旧包络上是 60%）。这不是标定失手——包络一拉宽，背一个数就更不管用，正是这条对照要显示的东西。

### 6.6 实测

## 7. 两条镜像轴与引道斜面（2026-09-09）

09-08 场景评审对本任务提了六条，当天落地四条（§6）。本节是剩下三条：**挡板初始在哪一侧**、
**边（敞口）朝哪一端**、**引道下坡**。做完之后本任务从「没有防捷径离散轴」变成有三条。

### 7.1 定稿前算掉的一笔账：真重力坡与慢球速打架

会上要的「引道下坡」如果用**真重力分力**做，和会上同时要的「球速放慢」是矛盾的，而且这个矛盾
不是取值没调好，是能量守恒定死的。

实心球在坡上纯滚动时 `m·g·h = ½·m·v² + ½·(⅖·m·r²)·(v/r)² = (7/10)·m·v²`，质量与球半径都约掉，
于是 **`v = √(10·g·h/7)`：到坡底的速度只由抬高 h 决定，与坡长、坡角各自无关**，长和陡只决定滚多久。

| 到门速度 | 需要的全程抬高 | `base_camera` 里占（256×256，一像素 5.24 mm） |
|---|---|---|
| 5 cm/s（包络下限） | 0.18 mm | 0.03 px |
| 10 cm/s（包络上限） | 0.71 mm | 0.14 px |
| 24 cm/s（判据 A 的上限） | 4.21 mm | 0.80 px |

画面里的比例尺：槽底板厚 9 mm = 1.7 px、闸板厚 12 mm = 2.3 px、导柱缝宽 18 mm = 3.4 px、
引道侧壁高 45 mm = 8.6 px。**整条 55 cm 引道从头到尾的高低差，是槽底那块板自身厚度的十三分之一，
在图里是七分之一个像素。** 而且坡越长，同一个抬高摊出来的角越小（55 cm 上 0.074°，1 m 上 0.041°）——
**加长坡道让坡更平，不是更陡**。反过来，一条看得见的 3° 坡会让球以 86 cm/s 到门，
封闭区往返只剩零点几秒，而闸板从下板到落座要 1.30 s：球早出门了，闸板才下到一半。

**取值：坡是看得见的几何，运动由驱动器给。** 这不是妥协，是回到本任务既有的口径——
`_ball_drive.py` 开头写的就是「送料轨设速度，不是重力设速度」，而坡道在 2026-08-17 正是因为
「浅到听凭求解器静摩擦摆布」被删掉的。代价照实记：指令加速度 3.9–56.5 mm/s²，
而同一坡角上真重力会给 306–611 mm/s²，差 11–66 倍。

「策略必须能从指令 + 出生画面里读出该做什么」，而球速此前是一条**只能从视频读、出生画面里

所以「架子在引道侧还是封闭区侧」四种组合都会出现。

### 7.3 镜像为什么这么便宜

`channel` 段里除 `door_y` 外每一条叶子表达的都是**离门多远**而不是绝对位置
（`entry_start_y: -0.550` 读作「引道从门外 55 cm 处起」），所以本任务每一条时序公式都是
两个这样的叶子之差、**对镜像不变**。真正经过镜像的只有「吐出或读取一个实际 y」的那几处，
统一走 `GateCageBallLayout.lane_y`（配置量 → 任务坐标）与 `.depth`（任务坐标 → 离门多深）：

| 处 | 改法 |
|---|---|
| `lane_bounds`、`ball_release_center`、`_add_channel`、`_add_far_wall` | 经 `lane_y`，区间取 min/max |
| 判定器 `inside`、障碍矩形的 y 端点 | 经 `depth` / `lane_y`，矩形端点排序 |
| `GateTriggerRule` 的 `inside` / 距离 / 「远离还是接近」 | 加 `inward` 字段，三处乘它 |
| `BallShuttle` 的初始方向、两个 demo 的 HUD 与量测 | `direction=int(layout.inward)`；量测改报 `depth` |

导柱、闸板、停放架的夹爪块都是**关于门对称**的，一处不用改。

### 7.4 出生门余量：从一个距离改成一个时间

09-08 把 `spawn_door_margin` 从 2 cm 提到 8 cm，为的是把「球最短能滚多久」从 0.53 s 抬到 1.21 s
（§6.2）——那是**拿一个距离代替一个时间**，而两者成正比这个前提在引道变斜之后就不成立了：
陡档的球起步慢，同样的距离买到更多秒数。

后果是可测的：坡把到门时刻拉长 1.29–1.6 倍，若下限仍按 8 cm 的距离算，**「球先到」的比例会从
16.6% 掉到 8.8%**（1000 seed 实测）——而 `hover_wait` 的正负正是三条触发规则拉开差距的机制，
任务文档写明它「只报告不约束」，不能为了别的目的被挤掉。这是 bar 那一轮那条规矩的又一次应验：
**一条新轴看起来免费，往往是因为没查它经过哪些既有读数。**

处置：拆成两条，各自写成它本来的量纲。`ball.spawn_geom_margin: 0.020`（几何：整球在门外，
这是距离）与 `ball.spawn_min_observe_s: 1.20`（观察：至少滚这么久，这是时间，距离按档派生，
`GateCageBallLayout._distance_for_observe`）。1000 seed 实测：球先到回到 **18.4%**（09-08 是 16.6%）、
观察时间下限 **1.21 s**、中位 5.34 s（改前 4.33 s——坡本身就把观察时间拉长了，这是会上要
「更宽裕的反应空间」的那一半）。

### 7.5 驱动器：分两段，以及步内重力增量

`BallShuttle` 在引道段按 `v(s)² = v0² + 2·a·s` 写速度，`a` 由「出生点到坡末端的距离」现算，
所以到门时刻仍是闭式解 `entry_delay = 2·s_ramp/(v0 + v_door) + 门前平段/v_door`，
两条可解性判据一行没改。

**加速段只作用在入门那一程**（按「腿」分而不是只按位置分）。位置型的速度曲线会同样作用在
**出门的球**上，那等于在闸板封门的地方摆了一段速度梯度：球在门口变慢 → 失速判据触发 →
驱动器反向 → 球在门口来回震荡而不是离开。出门必须仍是那个干脆的结局，所以球一旦进过门，
驱动器就恒定在 `v_door`。

**步内重力增量（2026-09-09 实测）。** 驱动器每步开头重写沿轨速度，管得到步边界、管不到步内；
斜面上重力在那一步内继续把球往下推，这一小段是净赚的。首跑 seed 3（5° 档）实测：
球在**第 768 步**过门，而闭式解是 819 步——早 6.6%，平均速度 0.0677 对指令的 0.0635。
前向欧拉积分只差 1 步，所以不是积分误差。反解出来每步相当于额外 **3.78 mm/s**；
纯滑动预测 4.26、纯滚动预测 3.04，求解器落在两者之间。

处置：`GateCageBallLayout.ramp_sag()` 按滑动式 `½·g·sinθ·cosθ·dt` 算出来，从指令速度里扣掉，
**只扣不加**（能写出比自己的时刻表更大的速度，正是 `HeadingDrive` 文档里记着的那个坑：
状态写入压过接触，球被从闸板底下顶过去），而且**只在球还在坡上时扣**（门前 2.1 cm 平段没有坡，
在那里扣会让到门速度低 4.3%，首次改完实测到）。取滑动式是因为它是上界，扣完球到得**偏晚**，
那是判据 B 的安全侧。

修后同一格实测：过门 **827 步**对闭式解 819（差 1.0%，偏晚）、到门速度 **0.1000** 等于指令值、
折返点 +0.0989 对预测 +0.0984、窗口 2.00 s 对预测 1.97 s。

### 7.6 场景搭建

引道那一组件（斜槽底 + 两侧引道墙）作为一个刚体整体，绕**坡与平段的交界线**
（轨道中心线上 `door_y − 2.1 cm`、`floor_top_z` 高度处）转一个角，所以两段槽底在交界处
严丝合缝，不用逐块凑 z（`_ramp_pose` / `_ramp_euler`）。槽底因此从贯通的一块拆成引道、
封闭区两块。绕 x 转的角在镜像下要变号——把 y 翻过来，绕 x 的转向也跟着翻。

`_add_ramp_support`：5° 时引道外端底面离桌 3.9 cm，加一块同色支撑。纯粹是画面需要——
这里每个固定件都是 `fixed=True`，没有它也不会掉，但一条远端悬在空中的送料轨读起来像建模失误
而不像斜置的轨道。支撑按它**内侧边缘**处的板底高度定，坡在支撑自身宽度上多爬的那一毫米留成缝：
本任务的件只相邻不共体积。

### 7.7 判据行

`checks()` 从九行加到 **十三行**，四条新的各对应一件此前由「碰巧成立」保证的事：

| 行 | 读数 | 门 | 默认 |
|---|---|---|---|
| `rack_reach` | 架心到机械臂底座 | ≤ 0.700 | 0.480（包络 0.474–0.566） |
| `carry_span` | 取板点到门口悬停点的水平距离 | ≤ 0.300 | 0.165（包络最长 0.280） |
| `release_on_ramp` | 出生点到坡末端的距离 | ≥ 0 | 0.379 |
| `entry_wall_over_center` | 引道侧壁顶高出球心多少 | ≥ 0.005 | 0.015（最大的球 0.009） |

后两行都是编辑守卫而不是抽样过滤器（包络最坏格都落在门内侧很远）。**「30 步的搬运跟不跟得住
28 cm」是实测项不是包络项**：把执行链的缺陷写进包络等于固化 bug 的形状，这是 09-03 那次角点
sweep 的结论（§5.3）。

### 7.8 架子挪远之后暴露的取板缺陷（approach 单独放慢）

`gate_rack.side` 把架子从门口旁 ±3 cm 挪到门两侧 ±15 cm 之后，seed 0–9 首跑 oracle **9/10**，
seed 4 判 `grasp_check_failed`：`finger_qpos = −0.0010`（手指合到底，夹了个空）、
`plate_yaw = 0.61°`（姿态没问题）。

**逐读数追下来的机制。** `lift_test` 那一刻手在 (−0.0421, +0.1766)、板在 (−0.0392, +0.1888)：
**板比手偏了 +12.2 mm**，也就是合爪之前板已经沿 y 被推走约 10 mm。板厚 12 mm，架子夹爪的
余隙只有每侧 3 mm，10 mm 意味着板整个滑出了指缝，所以合爪夹空、全靠 attachment 把它拎起来——
`min_finger_qpos` 这道门（09-03 立的）正是为这种「假成功」设的，它拦住了。

**是哪一条轴带来的。** 十格里九格 `finger_qpos` 都在 0.0063–0.0075（与 09-03 修后的区间一致），
只有 seed 4 是 −0.0010；相关的量不是架子的 y——seed 7 的 y 几乎一样（+0.171）却好好的——

**验证与处置。** 把每步位移减半（`steps_per_phase=60`）当场就好：`finger_qpos 0.0075`、

## 8. 正式设计改为自由滚动：重力斜坡 + 撞墙回弹替身（2026-09-10 定稿）

看过 §7 的视频之后提的两条：整套球和轨道往画面中间挪；球太慢——改成靠重力，
planner 按球的位置与速度实时定下板时刻，错过一趟球还会回来。

### 8.1 「弹回」是驱动器做的，求解器没有回弹

视频里球撞远端墙折返，是 `BallShuttle` 的失速检测在翻转指令速度，不是碰撞。09-10 复测
（`tests/ball_roll_spike.py` 的落球测试，scratch 里把 `coup_restitution` 注进球的材质）：
**0 与 1.0 的 `rebound_ratio` 都是 −0.001**，Genesis 1.2.1 刚体对刚体确实没有回弹可调，08-17 的记录成立。
关掉驱动器、其他不动，球撞平封闭区的墙会停死。

两条路（09-10 讨论）：远端做成坡（V 槽，重力让球回头）；或封闭区保持平的、在墙上放一个回弹替身。
取了后者——引道靠重力，驱动器只在球撞墙停死那一刻按撞前速度 × `ball.wall_restitution` 反向写一次，
然后交回重力（`_ball_drive.WallRestitution`）。与 `offtrack_decel` 同一类：求解器缺的物理用一个写明的常数补，
只在该起作用的地方起作用。只认三个面（远端墙、闭合闸板的外侧面、闸板的内侧面）；
板底下那条带内停住的球不弹——那是被板压住，判定器记作 pinched。

### 8.2 趟次表：每撞一次慢一截，每一趟停留更久，planner 挑第一趟封得住的

球从松开高度 h 滚下（到门速度 √(10·g·h/7)，只看 h），穿过平的封闭区，撞墙后以 e 倍速度回来，
出门、爬引道到较低处、再回来。第 n 趟入门速度 eⁿ·v₀，停留 `L/v + L/(e·v)`。
探针格：5°、引道 35 cm、封闭区 30 cm、松开点 25 cm、e = 0.80、轨道 center_x = 0（对着 `base_camera` 的视线）：

| 趟 | 预测 到门时刻 / 入门速度 / 停留 | 实测（inspect，无机械臂） |
|---|---|---|
| 1 | 0.91 s / 52.9 cm/s / 1.15 s | 0.91 / 52.8 / 1.17 |
| 2 | 3.54 / 42.3 / 1.44 | 3.55 / 41.7 / 1.47 |
| 3 | 6.21 / 33.8 / **1.79**（封门要 1.45，第一趟够的） | 6.22 / 32.7 / **1.87** |
| 4 | 9.04 / 27.1 / 2.24 | 9.09 / 25.4 / 2.41 |
| 5 | 12.19 / 21.7 / 2.80 | 12.35 / 19.4 / — |

到门 52.8 对预测 52.9——求解器里球是纯滚动的，`(5/7)·g·sinθ` 分毫不差。第 4 趟起实测比预测慢约 4%，
是求解器自己的一点耗散，方向是安全的（停留更长）。

**判据的变化。** 判据 B（臂就位时球还没走）消失：球会回来。换成三行：
`window_margin` 现在读**可用那一趟**的停留（`sealable_pass`：t_ready 之后、悬停上限之前、停留 ≥ 封门时长的第一趟）；
`ready_margin` 读那一趟离上限还有多久；新行 `moving_at_cap`——上限到时球入门速度 ≥ 10 cm/s，
不然「一直悬停等球死在墙根再插」成了捷径（探针格 17.3 cm/s）。`bounce_when_free` 守 e ≥ 0.3。
出生点的上界只剩几何（整球在门外），1.2 s 观察下限那条只对驱动模式有意义。

### 8.3 planner：按位置与速度算「回到门口还要多久」

`GateTriggerRule` 加 `restitution` 与 `turn_depth`：球向墙去时 `(L−s)/v + L/(e·v)`，向门来时 `s/v`，
够封门时长 + 富余才下板。首跑 oracle 在 4.20 s 下板——正是第 2 趟撞墙那一瞬：撞墙时求解器有一两步报出
接近 0 的速度，`距离÷速度` 算出无穷长的余量。修法：`velocity_floor` 0.05 m/s 以下的读数一律不当真
（`inside_velocity_unreadable`，等下一步真实的回弹速度）。那一格照样判了成功，机制是板下到球顶以下时
本身就是一堵墙，出门的球撞上正在下降的板被替身弹回门内——物理上说得通，但 planner 的决定是错的。

**planner 修后重跑（13:11，`runs/gate_cage_ball_variation/20260910_showcase/free_bounce_oracle_oblique.mp4`）：**
`hover = 352 步` ⇒ **6.22 s 下板，正是第 3 趟入门的那一刻**（趟次表 6.21 s），触发理由
`inside_returns_in_time`，`success=True`、`caged=True`、`finger_qpos 0.0074`、`plate_yaw 0.09°`。
planner 放过了停留不够的前两趟，等到第一趟够的——这就是「按位置与速度实时决定」要的行为。

**已加固：** 低速撞墙时停止分了两步，替身抓到的是第二步的速度（第 5 次撞墙记到 0.101 而非 0.194），

机制：e = 0.80 衰减快，球到上限时已慢到几乎一直在门内。

可行区间：0.90 时短封闭区上陡坡只剩 10–16 cm，**0.85 时全部 10–33 cm 可行**，构造式成立。取 0.85。

一个方法论上的坑记一笔：我第一次扫 e 时在 `randomize_task_cfg` 外面 try/except 数拒绝，得到「0.90 拒绝 0%」——
那个函数**内部会重抽直到接受**，外面永远数不到拒绝，正确的量法是随机化门用的 `_first_draw_rejected`。

### 8.5 封门时限是"板底过球顶"，不是"落座"

fixed 7/10 对离线模型的 24.3%（n=10 下 P(≥7) ≈ 0.4%），不是噪声。模型把「下板到封住」算成落座时长 1.30 s
（`insert_duration`），但闸板板底一降到球顶以下就是一堵墙——判定器的 `gate_blocking` 与替身的闸板面判定
用的都是这个高度。按 `insert_steps` 100 步的余弦下降、板底从 0.146 到 0.012、球顶 0.057–0.081：
板底过球顶在下降的 49–66%，折成时间 **0.49–0.61 s**（球越大越早）。所以真实可封的趟比模型多一倍，
fixed 才到 7/10，oracle 也因此过于保守（悬停 1.7–9.8 s，本可更早）。

处置：`GateCageBallLayout.block_duration()` 由几何现算，`seal_deadline()` 在自由球下取它、驱动球下仍取落座时长
（驱动器会把球顶进没落座的板）；`window_margin` / `sealable_pass` / planner 的时限都改读它。

时限改完的三道门：几何门 24 角点全过，新增不变量「板底过球顶 0.606 / 0.548 / 0.490 s，球越大越早、都短于落座 1.30 s」；
随机化门 1000 seed 拒绝率 0.000；解析角点 1152/1152、0 拒。`fixed_delay_s` 重标 **15.25 s → 511/1000**。

**要如实记的一处变化。** 时限从 1.45 s 缩到 0.64–0.76 s 之后，可用趟几乎总是第 2 趟
（{2: 892, 3: 105, 4: 3}；第 1 趟 0.66–1.47 s 到门，早于臂就位 2.70 s）。「等哪一趟」这条机制因此变薄，
不感知策略的上限从 24% 升到约 51%——那就是球在上限附近处于门内的时间占比。oracle 100% 对
greedy / fixed 各约 50%：分得开，但不如驱动版那么远。这是"板一过球顶就是墙"这条物理事实的直接后果，
不是标定；要拉开只能从别处来（比如缩短悬停上限让 fixed 没法等到球慢下来，或把封闭区做短让每趟停留更短），
留作后议，这一轮不动。
