# Hedgehog / Claws 新机制：scripted policy 开发与全流程验收

日期：2026-09-27。状态：**已开展首轮实施；P0、反馈执行器、几何搜索与抓持诊断已接入，P1/T2 未通过，尚无新的完整解题成功记录。** 用户确认首批只做两个 medium，easy / hard 做回归。实际结果见[首轮实施与证据](../../../runs/test_results/hedgehog_claws_policy_20260927/README.md)。承接[初始化场景反馈与开发报告](initial_scene_feedback_20260927_zh.md#9-本轮开发与验证2026-09-27)。

下一轮优先完成 **Hedgehog medium 椭圆窗**、**Interlocked Claws medium 锐角双窗与 J 钩**的可执行 scripted policy，并从各自规定的 segment0 连续运行到任务结束。先核验几何通路和真实夹爪的可操作性，再开发反馈控制与完整验收；不能预设当前几何一定有解，也不能用末态成功掩盖中间卡滞、穿透或突跳。

## 1. 范围、优先级与当前证据

| 对象 | 本轮已有证据 | 下一轮要求 |
|---|---|---|
| Hedgehog medium | 深色实木、六个竖向椭圆窗；初态和若干抬升姿态检查；初始化短片 | 验证完整刺球与夹爪的出笼通路，执行接近、抓取、抬升、定向、出笼和终态确认 |
| Claws medium | 原 ALOHA 夹爪完全相对并持件；中央互锁；直拉受阻；0.5 s 抓持检查 | 验证两扇窗的连续通过路线、两次定向是否确有必要，执行完整分离和终态确认 |
| Claws hard | 保持 0.5 s 时抓持位置偏移约 1.1 / 1.5 mm，但两件相对夹爪转角约 10.6° / 17.3° | 另列抓持稳定性修正和复测；它不是 medium 开发的共同前置条件，也不因 medium 成功取得完整解法资格 |
| Orbits hard | 向上弹起减轻，但初始绳形仍会重新排列 | 另列初态平衡及绳长需求验证，不纳入本轮两个刚体 policy 的交付范围 |

第一批只交付这两个 **medium 新机制**。共享控制或判据改动需回归受影响的 easy / hard，但不将范围扩展成六个变体的完整解题开发。旧版 oblique_gate、orthogonal_gate 和历史演示只作算法参考，不能继承成功标签。

开发顺序及进入下一阶段的条件：

1. **P0：冻结输入与验收合同。** 固定源码、资产、机器人、初态、判据版本及参数；确认观测、接触与完整碰撞几何可读取。
2. **P1：几何路线与抓持可行性。** 找到完整物体通路，并检查真实夹爪、握柄及机械臂能否执行；完成关键错误动作和捷径搜索。若不通，先定位阻挡，再修订几何或抓取路线，保留版本差异。
3. **P2：反馈式 policy。** 分阶段实现，使用实测状态进入下一阶段；在 Genesis 中逐段调试，然后从原始 segment0 连续重跑。
4. **P3：完整物理与终态资格。** 独立审查全过程、当前任务目标和判据，再完成同初态复现及时间步复核。
5. **P4：录像、归档及索引。** 只有通过相应级别的运行才更新完整流程标签；初始化录像与完整解题录像保留各自含义。

## 2. 初态与“完成”的定义

### 2.1 起点

- **Hedgehog：** Panda + Robotiq 从当前机器人配置的默认 home 开始。录像包含连续接近、实际夹持和后续解题；不能把物体预先抬到窗口中央，或从抓取附近的 IK 姿态替代接近过程。沿用深色实木笼、原十刺球及当前桌面布局。
- **Claws：** 遵守用户针对本任务的明确要求，segment0 已由两个原 ALOHA 夹爪夹住两件 claw，中央处于互锁状态；medium 采用完全相对的初始夹爪姿态。此任务特定起点优先于通用的 home 接近演示约定，报告标明 `pregrasp`，不补做松爪再抓的片头。
- Claws 不修改机器人 mesh、碰撞体、关节限位或公共 home。两件 claw 保持独立刚体；初始指距和闭合控制目标都纳入状态身份及回溯检查。不得增加焊接或隐式辅助约束来维持握持。

### 2.2 机制完成、当前 Task 成功与物理资格分别记录

**机制完成：** Hedgehog 的整个刺球（包含全部尖刺）完全离开笼子；Claws 的两件完整分离，随后短暂停稳，允许保持抓持。只露出球心、钩头通过第一扇窗或物体中心距离增大，都不算完成。

**当前已部署的 Task 合同还有目标区要求。** [2026-09-25 终态计划](terminal_judgement_engineering_plan_20260925_zh.md)记载后续加入绿色虚线目标区；当前两项任务均使用 [PlacementGoalMixin](../../../topogym/tasks/placement.py)：

| 当前任务 | 目标物 | 当前结束要求 |
|---|---|---|
| Hedgehog | `hedgehog_ball`，包含全部尖刺 | 完整进入固定目标区，笼子及底座保持在系统一侧；保持低速持续 2 s，允许握持 |
| Claws | `placement_targets` 指定的棕色件；新 medium 构建时为 `piece_0` | 完整进入固定目标区，其余部件留在系统一侧；保持低速持续 0.5 s，允许握持 |

实现时读取实际 Task 声明和区域身份，不硬编码历史实体名。Claws 即使主要移动蓝钩完成解锁，后续也须规划棕色目标件的入区动作；不能将蓝钩当成可互换目标。两项均不额外增加放桌、松爪或撤手条件。目标区路径在 P1 一并核验。

早期 Claws 文档的“分离停稳即可”与当前目标区合同范围不同。报告须分别给出 `mechanism_completed`、`task_success` 和过程物理资格；本文沿用当前部署合同，不借 policy 开发悄悄删掉目标区。若后续调整任务目标，应在 Task 中明确修订、更新身份并重验，不能仅改 policy 自报结果。

当前 `PlacementGoalMixin.goal_complete=False`，两项尚未取得完整终态资格。先用独立证据审查真实执行，再按已验证的变体范围完成判据资格接入并重跑正式 terminal；**不能为得到 True 临时 monkeypatch，也不能在公共 mixin 中一次性为所有分离任务开启资格。** `act()` 返回 `None` 只表示脚本结束，不等于成功。

## 3. Policy 接口与控制要求

复用 [scripted policy 合同](../modules/scripted_policy_execution_plan_20260926_zh.md)、[本地 simulator API](../modules/simulator_api_zh.md)及 [ScriptedPolicy](../../../topogym/planning/base.py)：

```text
管理方创建 Env 并 reset 到任务规定的 segment0
    → SegmentRunner.run_policy(...)
    → 授权后的 obs → policy.act(obs) → 一条原生 action
    → 既有 Env.step → Genesis → 下一个 obs
    → Task 终态或明确的 policy/执行失败 → 封存证据
```

- 首版采用 **unlimited、使用授权物体真值的参考策略**。它用于验证机制和机器人可执行性，不声明为 RGB-only / limited 视觉策略。管理方显式授权 `state_fields`，优先 `world`，确需当前任务状态时再加入 `task`。
- 机器人本体来自 `obs.robot`；物体实测状态来自获准的 `obs.privileged`。在接入时核对 body、姿态、速度和接触的实际 schema。未导出的距离由已授权位姿和冻结几何计算；缺失的必要传感证据应补接口或报告缺口，不填零、不猜测抓持成立。
- `initialize(context)` 检查机器人、动作格式、观测字段、单位、四元数顺序及控制周期。构造参数中的几何、抓取候选和参考路线也属于明确声明的 oracle 输入，进入提交哈希。
- 优先采用 `EE_ABS`，输出世界坐标 TCP 目标和当前机器人规定的夹爪字段；若可达性要求改用 `JOINT_ABS`，在创建该 Env 前选定，不能同一 episode 混用动作格式。
- policy 只产生动作，不持有 Env / World / Interaction，不调用 `step/reset/rewind`，不设置物体位姿，不直接 attach/detach。低层 FK/IK 及碰撞计算复用现有模块，不另建物理循环。
- 每个阶段包含进入条件、实测完成条件、最大仿真时长、停滞判定和失败原因。插值只生成参考；不能仅因预设秒数或动作列表耗尽就进入下一阶段。
- 使用实测物体—TCP 相对变换检查抓持。位置和角度同时监测；手指闭合不等于抓住、物体位置不变也不等于抗转稳定。
- 每步限制位移、角度变化和加速度；窄口阶段根据剩余间隙及跟踪误差减速。超差后先停止推进，只有有足够空间且抓持正常时才沿已验证前缀有限回退；禁止无界重复顶撞。
- 等待通过保持动作推进物理，按实际仿真时间计时。`{}` 保持既有控制目标；重复 delta 指令会继续移动，不能用它代替保持。
- 正式基线继承当前默认时序：`physics_dt_s=0.0025`、`control_decimation=10`、`solver_substeps=4`。不要复制方块长程样板的显式加速时序。总时长预算根据路线设置并记录，不能把超时写成成功。
- 首版两项均以真实手指接触抓持为验收基线，公共 grasp assist 关闭。若另做 assist 诊断，单独记录，不能替代该基线；Claws 尤其不能用 assist 掩盖抗转问题。

## 4. Hedgehog medium：路线与阶段指引

### 4.1 建模机制与几何搜索

当前 [椭圆窗生成器](../../../topogym/assets/geometry/hedgehog_ellipse.py)给出笼高 240 mm、窗口高 224 mm、中央最大宽 58 mm、球核直径 54 mm、六窗均匀间隔 60°。仅按球核直径估算，球心穿过窗口中面时的必要高度范围约为笼中央上下 40.9 mm；**这个范围不是完整刺球的可通行证书**。

建立每扇窗的局部坐标：径向向外、沿周向、竖直。搜索完整球体位姿的连续路径，变量至少包含高度、径向位移和三维朝向；不能只试球心直线或单一轴旋转。以下是动作结构假设，不预先指定“转多少度就能过”：

```text
从低处真实抓住刺球 → 在笼内抬向中央宽区
    → 找到完整尖刺的通过朝向 → 边旋转边向外退出
    → 最后一根刺越过笼壁 → 入区并保持稳定
```

几何搜索应包含所有尖刺、8 mm 笼壁厚度、上下封闭端和底座。沿途对实际夹爪指尖、掌部及机械臂做联合检查；球能过但夹爪进不去、转不了或退不出的路线应淘汰。先搜索现有刺球上可夹持的部位，不默认为某一根刺天然适合作握柄。

优先找一次抓持可完成的路线。若必须换抓，需要证明中间可支承或稳定停放，再设计真实释放、重新接近与抓持；不能在空中切换绑定，也不能自动为刺球增加新握柄。找不到路线时输出阻挡部位、最近距离与不可达姿态，作为后续建模修订依据。

### 4.2 阶段状态机

| 阶段 | 动作 | 进入下一阶段的依据 / 主要失败条件 |
|---|---|---|
| H0 初态审查 | 从 home 观察笼子、球和目标区 | 模型身份匹配，初态合法，路线及抓取候选与本实例一致 |
| H1 接近与抓取 | 从窗口接近已检查的夹持部位，闭合手指 | 双侧接触或等效可靠抓持证据，加小幅试抬；空抓、夹爪撞笼或球打滑则失败 |
| H2 抬到宽区 | 保持抓持，按笼内安全路径抬升 | 实测球位姿进入已验证的出笼路径起点；不能仅检查 TCP 高度 |
| H3 定向 | 在尚有空间的位置旋转、倾斜刺球 | 整体尖刺和夹爪均满足下一段的间隙要求；无持续卡滞或角度滑移 |
| H4 连续出笼 | 联合旋转与向外平移，必要时分多个姿态区间 | 最后一根刺也已完全退出；球核或球心先出不触发完成 |
| H5 分离确认与入区 | 确认笼外状态，沿安全路径将整个目标送入固定区域 | 全部尖刺入区，笼子/底座位置正确，机器人和目标无非法接触 |
| H6 稳定确认 | 保持姿态，按 Task 时间窗继续 step | 当前合同完整成立持续 2 s；独立检查、TaskResult 和运行证据一致 |

H2–H4 可以由多段平滑参考轨迹实现；阶段名称不要求机械地先完成全部抬升再完成全部旋转。若通路需要两者交织，应以实际连续路径为准并记录动作因果。

### 4.3 机制对照

- 在初始低位及更靠近顶部的窄区尝试完整刺球出笼，记录哪根刺或球核被哪里阻挡。覆盖六扇窗，不能只验证面对机械臂的一扇。
- 对比不抬升、只抬升不改变朝向、只直线外拉和已找到的有效联合路线。错误动作的“受阻”由接触/间隙及进展量共同说明，不能只看电机没有跟上。
- 检查大幅倾斜、邻窗路径以及顶部/底部是否允许绕过预想限制。如果低位确实可完整通过，应记录为机制反例并修订设计，不能只保留偏好的演示路径。
- 报告各出口搜索的高度范围、朝向覆盖、搜索预算及最小间隙。有限搜索未找到捷径只能写“在这些范围内未发现”，不能写成对所有姿态的不存在证明。

## 5. Interlocked Claws medium：路线与阶段指引

### 5.1 建模机制与相对运动

当前 [双窗与 J 钩生成器](../../../topogym/assets/geometry/claws_opposed.py)包含夹角 55° 的两个窗口、后侧 U 形框和抓持握柄；蓝钩杆初始穿过两扇窗，钩头位于第一扇窗外侧。初始约 2.5 mm 的最小表面间隙只说明初态，不能作为全过程余量。

以棕色窗架为参考系规划蓝钩的相对位姿：`T_frame_hook = inverse(T_world_frame) × T_world_hook`。先搜索：

```text
确认双手稳定持件 → 对准第一窗 → 钩头完整通过第一窗
    → 在两窗间重新定向 → 钩头完整通过第二窗
    → 两件完全分离 → 按当前目标区合同收尾并稳定
```

窗口夹角 55° **不等于**第二次需要转 55°；转轴、角度及平移必须由完整钩形、杆长、窗口厚度、U 形框和机器人空间共同决定。不能把概念图中的姿态直接当作动作常量。

先尝试左手保持窗架、右手移动蓝钩，但左手保持是实际控制，不把窗架固定到世界。若单手相对运动超出可达范围，允许双臂协同；必须保留要求的 segment0、真实夹持和同一条相对解锁路线。两窗间没有足够空间转动或长杆撞窗时，返回几何层修订，不能关闭碰撞或强行压过。

### 5.2 阶段状态机

| 阶段 | 动作 | 进入下一阶段的依据 / 主要失败条件 |
|---|---|---|
| C0 初始持件确认 | 保持原闭合目标，测量双侧 claw—TCP 变换 | 两件仍互锁，抓持位置/朝向稳定，无初始严重穿透；超差需修正初态或握柄 |
| C1 第一窗定向 | 根据相对位姿调整钩头朝向 | 钩头及杆身的完整下一段路径可通，另一只手持件稳定 |
| C2 通过第一窗 | 小步抽拉并配合已规划旋转 | 整个钩头越过第一扇窗的有限厚度区，仍受第二扇窗约束 |
| C3 两窗间重定向 | 在窗间执行第二段不同的朝向调整 | 已通过部分不重新撞第一窗；杆、钩尾、握柄和手指均留有余量 |
| C4 通过第二窗 | 沿验证路径退出 | 钩头与杆身全部脱离窗口约束；不能仅看两件 AABB 中心距离 |
| C5 分离与目标区动作 | 在足够间隙下确认完全分离，将指定棕色件送入目标区 | 目标身份正确，蓝件仍在系统一侧，双臂不互撞；允许持续抓持 |
| C6 稳定确认 | 双手保持，执行 Task 的确认窗口 | 当前合同成立持续 0.5 s；独立过程检查与 TaskResult 一致 |

### 5.3 两次定向与捷径验证

- 直线抽拉、第一窗姿态直接穿第二窗、固定一个朝向穿两窗、反向退出、横向绕开以及利用 U 形框空隙分别搜索或做有限动作对照。
- “两次定向”不能按 policy 阶段名证明。应记录钩头通过第一窗和第二窗时的真实相对朝向、差异、窗口接触/间隙，以及将第一窗姿态保持到第二窗时的阻挡证据。
- 搜索多个固定朝向及平移路线，检查是否存在一次预转后即可穿过两窗的捷径；搜索覆盖和数值容差进入报告。若找到有效捷径，则“两次定向必要”不成立，即使某条两次转动演示能成功。
- 通过窗口事件应依据完整钩头/杆身在有厚度窗口中的运动和连续无穿透记录，不能只以某个中心点跨过平面计数。
- 基线使用连续抓持；如另发现通过真实支承换抓可以绕过设计，应报告其动作与任务规则适用性，不隐瞒该路线。

## 6. 数值容差与过程质量

所有阈值在测试前固定进配置/报告，区分“当前 Task 阈值”和“本轮拟采用的开发阈值”。以下为开发起点，需要用真实运行标定，不能描述为已通过：

| 项目 | 要求 |
|---|---|
| 被动持件 | 两项抓取完成后至少测 2 s；记录最大相对平移和转角、速度及接触。可先以 2 mm / 3° 作为抓持漂移上限，再根据窄口真实间隙收紧；这些数值不自动保证通行 |
| 间隙预算 | 跟踪平移误差 + 转角在物体外缘造成的位移 + 抓持漂移 + 碰撞表示/距离计算误差，应小于路线最小可用间隙；不足则改路线、改善控制或建模 |
| 连续路径 | 优先连续碰撞检查；否则自适应细分并给出平移/转角引起的最大表面运动界和距离误差界。只有离散无碰撞点而没有段内依据时，标为 sampled，不能称连续证书 |
| 接触 | 夹持接触与任务允许的导向接触单独列出；不得把它们一概当失败。记录禁止接触、穿透深度、力/冲量峰值及卡滞，覆盖全部物体和机器人几何 |
| 运动质量 | 保存期望/实测 TCP 与物体轨迹、进展量、速度、角速度和抓持滑移；出现持续顶撞、突然跳过窄口或物体掉落，即使末态入区也不通过过程验收 |
| 终态 | 当前目标区速度限值为 0.001 m/s、0.02 rad/s；分别确认 2 s / 0.5 s。按实际 Task 版本读入，资格标定后的修订另记版本，不在结果出来后放宽 |

真实物理检查说明采样粒度：每 physics tick 的记录不能自动证明求解器所有子步都无碰撞；接触事件有子步覆盖时记录其来源，覆盖不足明确说明。

## 8. 开发与测试矩阵

| 层级 | 必须覆盖 | 通过后能说明什么 |
|---|---|---|
| T0 静态与合同 | 模型/资产身份、action/observation 合同、坐标/单位、真实初态、目标物与区域、权限 | 接口和测试对象明确；不代表可解 |
| T1 完整几何路径 | 所有尖刺或钩身、窗口厚度、握柄、笼/窗架；段内检查和最小间隙；完整出口状态 | 在声明误差和范围内存在物体通路；不代表机器人已执行 |
| T2 可达与抓持 | 全程机器人 IK/关节限位/自碰/环境碰撞；接近、保持、旋转负载与真实抓持 | 候选路线适合当前机器人；短程实测与全程资格仍分开 |
| T3 机制反例 | 第 4.3 / 5.3 节错误动作与捷径搜索；明确搜索覆盖 | 支持或否定设计机制，有限搜索不冒充普遍证明 |
| T4 完整 Genesis | 从规定 segment0 连续运行；无瞬移、关闭碰撞、外力搬运、隐藏绑定或拼接成功段；全过程质量通过 | 该配置的一次真实机器人完整执行 |
| T5 终态与反例 | 完整目标入区、稳定时间、失败优先、证据缺失；目标互换、仅中心入区、尖刺/钩尾未退出、未稳定都不得成功 | 判据不误报；实际 TaskResult 仍需当前变体资格接入与重跑 |
| T6 复现与时序 | 相同冻结配置至少 3 次独立 reset 完整执行；基线另做半时间步复核，保持控制周期不变 | 指定条件的重复性和时间步敏感性；不代表普遍成功率 |
| T7 回溯与段衔接 | 同 episode 的 segment0 与中途状态恢复；物体、关节、夹爪目标和 Task 窗口一致；相邻段首尾 state_ref 连续 | 恢复和证据链有效，不增加独立成功次数 |
| T8 媒体与交付 | Nyx 多视角同步、全量解码、时长、SHA-256、帧与真实状态对应、链接有效 | 视频对应已声明的那次运行 |

关键反例测试须与失败原因对应：例如“固定朝向抽不出”的测试若实际因 IK 超限或脚本异常停下，不能算几何阻挡通过。单测主要检验真实易错条件及反例，不为每个 waypoint 镜像写断言。

同配置复现采用冻结后的同一份 policy 与参数，要求三次独立 reset 连续执行均通过全过程和终态检查；保留此前所有失败，不从多次尝试中挑三个成功冒充三次全过。额外可运行 seeds 0–4，但先比较实际资产/初态身份：若固定变体在不同 seed 下完全相同，只能算重复运行。小幅位置、朝向或抓持扰动应在合法 Task 配置/测试夹具中创建并单独标识；不得在 episode 中直接挪动物体制造起点，更不能将未支持的随机化说成已验证泛化。

半时间步建议使用 `physics_dt_s=0.00125`、`control_decimation=20`，保持名义 40 Hz 控制并显式记录 solver 参数，至少完成一次全过程和终态检查。比较通路事件、穿透、抓持漂移和成功结果；只有失败、新改动或未解疑点才扩大测试。CPU 无 RGB 可用于纯物理诊断，正式视觉证据必须来自 CUDA / Nyx，不能静默改渲染后端。

回溯用于调试，不用于拼出一次成功。Env rewind 不会自动恢复 Python policy 的内部阶段/生成器；管理方应新建 policy 并从恢复后的 obs 与明确的续段参数初始化，或使用带身份校验的 policy checkpoint。不能继续使用指向已作废未来的旧内部状态。最终资格运行仍从原始 segment0 连续重跑。

## 9. 产物与完成标准

新完整 policy 执行沿用当前 rollout 目录约定，例如：

```text
task_rollouts/hedgehog_claws_policy_20260927/
  hedgehog_in_cage/rollout_0001/
  interlocked_claws/rollout_0001/
```

后续递增编号，保留失败尝试；日期按实际实验记录。纯几何和短程专项检查放 `runs/test_results/<experiment>/`，在 rollout 报告中引用。同一执行的源码快照、资产与配置身份、逐 tick 状态、动作、阶段事件、接触/间隙指标、终态报告和录像均需可追溯。

每份报告至少记录：变体与 model/terminal revision、seed 与真实初态身份、机器人及 assist 设置、物理时序、policy 源码/参数哈希、路线身份、请求与 segment/state 身份、阶段起止、失败原因、完整物体/夹爪轨迹、关键间隙、机制对照结果及搜索覆盖。结果分别列 `geometry_path_verified`、`robot_execution_verified`、`mechanism_evidence`、`task_success`、`process_quality_passed`；未知或未运行不得写为 True。

录像使用 [公共 recording 模块](../modules/recording_module_usage_zh.md)，沿用 prepare、session/replay、validate、archive，不另写取帧循环或编码器。Nyx + compact_lab，848×480、30 fps；Hedgehog 保留 agentview / front_oblique / wrist，Claws 保留 cam_high / cam_low / cam_left_wrist / cam_right_wrist。正式录像必须覆盖同一次连续执行的规定起点、关键通过动作和最终稳定窗口。

正式收录时使用 `demos/<task_id>/varaition_<variant_id>/<camera>/`，采用当前 catalog 确认的变体目录，不能把新 medium 覆盖成旧家族已验证视频。视频叶目录只放独立 MP4，配套证据按现有约定放 `runs/demo_metadata/`；更新任务页、Demo 索引及原反馈报告，初始化索引仍保持 39 项正式变体结构。

**本轮完成条件：** 两个 medium 各有可复用 policy、一条经过几何和机器人检查的完整通路、真实连续物理执行与复现证据、明确的机制对照结论、当前 Task 的正式终态结果，以及可直接查看的同步完整录像。若几何无解、存在捷径、抓持不稳或目标区不可达，应明确记为该阶段未通过并给出修正项；单段调试成功、末态截图或初始化短片不满足交付。
