# TopoGym 框架 — 功能模块拆解（新人友好版）

> 状态：**初稿 / 顶层视角**。本稿只回答四件事：**(1)** 谁负责造环境、**(2)** 谁负责跑机器人和 RL 算法、**(3)** "agent 在 env 里交互"那条循环是别人给的还是我们自己写的、**(4)** 我们要支持哪几种使用模式。不写任何 API 细节，每个模块都用日常话描述"管什么 / 不管什么 / 谁来提供"。后续每个模块再各自开 design doc。

---

## 0. 我们在谁的肩膀上 / 我们要补什么

TopoGym 不是从零写一个引擎，它是在两个**已经存在**的东西之上拼装：

| 已有的东西 | 它提供什么 | 它**不**提供什么 |
| --- | --- | --- |
| **Genesis**（物理仿真器） | 一个"世界"，里面可以放桌子/机器人/绳子，按 dt 推进物理。**支持把 N 个相同世界一次性塞进 GPU 同步演化**（这就是我们说的"批量"）。 | 任务是什么、什么算成功、奖励怎么给、policy 长什么样、训练怎么训。 |
| **rsl-rl**（RL 算法库） | 训练循环 + PPO/SAC 等算法的实现。**只要你的环境符合它要的接口，它就能直接训。** | 环境本身、奖励、观测、控制器。 |

→ **中间所有缝隙都是 TopoGym 要写的**：怎么把一个拓扑任务翻译成 Genesis 里的场景、机器人能做什么动作、policy 看什么观测、怎么把环境包成 rsl-rl 能吃的形状、怎么同时支持采数据和评测。

---

## 1. 八个功能盒子（这就是整个框架）

每个盒子就是一个独立小模块，组合起来覆盖"造任务 → 训练 / 采数据 / 评测 → 出结果"的全流程。

### A. 造世界 (World Builder) — `topogym.world/`
- **管**：在 Genesis 里把一个具体任务的场景搭起来——放桌子、放机器人、放 5 根绳子、放 4 个目标格、设置初始位置。
- **不管**：不管什么算成功、不管奖励、不管观测。
- **谁提供物理能力**：Genesis。我们只写"放什么、放哪里"。

### B. 任务定义 (Task) — `topogym.tasks/`
- **管**：这个任务到底想干嘛——**什么算成功**、**每步给多少奖励**、**什么时候结束**、初始状态怎么随机。
- **不管**：不管机器人是哪一款、不管 policy 是神经网络还是 VLM。
- **依赖**：盒子 A。

### C. 机器人 & 动作接口 (Embodiment) — `topogym.embodiment/`
- **管**：把机器人加载进场景；定义"一个动作"到底是什么——
  - 关节角度? （最底层）
  - 末端执行器的位姿? （中间层）
  - "抓这根绳头、放到那个格子" 这种高层原语? （最抽象）

  然后把动作翻译成 Genesis 听得懂的关节力矩 / 位置命令。
- **不管**：不管 policy 怎么决定输出动作。
- **谁提供机器人模型**：Genesis 接收 URDF/MJCF 文件，我们把模型文件管起来。

### D. 观测打包 (Observation) — `topogym.obs/`
- **管**：policy 每一步**能看到什么**——
  - 一张俯视图? 多视角 RGB?
  - 机器人本体的关节角、速度?
  - 当前绳子结构的符号化拓扑信息?
- **不管**：不管 policy 怎么用这些数据。
- **谁提供原始数据**：Genesis 的相机渲染 + 状态读取。

### E. Policy (策略) — `topogym.policy/`
- **管**：接收观测，输出动作。可以是：
  - **神经网络**（被 RL 训练 / 模仿学习训出来）
  - **大模型**（GPT / Claude / Gemini 看图给指令）
  - **写死的脚本**（用作 oracle 或 baseline）
  - **随机**（用来 sanity check）
- **不管**：自己是在训练、采数据还是评测——这是上层"使用模式"管的事，policy 本身不知道。
- **依赖**：盒子 C（动作长什么样）+ 盒子 D（观测长什么样）。

### F. Agent ↔ Env 交互循环 (Runtime) — `topogym.runtime/`

这是**整个框架的承重墙**，也直接回答你的问题 3。

> **核心事实**：Genesis 只给"物理 step"，rsl-rl 只给"算法侧训练循环"，**没人给"agent 在 env 里交互"那条循环**。这条循环必须 TopoGym 自己写——但只写一次，三个使用模式共用。

- **管**：把上面 A/B/C/D/E 接到一起，跑这条经典循环：
  ```
  obs = env.reset()
  while not done:
      action = policy(obs)
      obs, reward, done, info = env.step(action)
  ```
  并且 **N 路同时跑**（Genesis 的批量能力在这层暴露出来）。
- **额外关键职责**：把这个 env 对象**包装成 rsl-rl 期望的形状**（rsl-rl 要的接口和标准 Gymnasium 略有不同，要适配一下）。包好之后：
  - 给 rsl-rl 用 → 在线 RL 训练
  - 给我们自己写的简单循环用 → 离线采数据 / 评测

### G. 三种使用模式 (Use Modes)

建在盒子 F 之上的三条互不干扰的路径——**都共用同一份 runtime**，只是数据消费方式不同：

| 模式 | 谁来驱动循环 | 用 policy 干嘛 | 产出 |
| --- | --- | --- | --- |
| **在线 RL 训练** `topogym.train/` | rsl-rl 的 PPO/SAC 训练器 | 边交互边**更新 policy 参数** | 训练好的网络 checkpoint |
| **离线数据生成** `topogym.data/` | 我们自己的简单循环 | 用 oracle/scripted policy 走一遍 | **轨迹文件**（observation, action, reward 序列） |
| **评测 (Eval)** `topogym.eval/` | 我们自己的简单循环 | 用任意 policy 走一遍 | **打分报告** + 可视化 GIF |

### H. 配套设施 (Glue)
- **配置** (`config/`)：所有参数（seed、n_envs、相机分辨率、奖励权重 …）都写在 YAML 里，命令行可覆盖。
- **注册表** (`registry/`)：任务/机器人/算法 用字符串 ID 索引（`task=knots_untangle robot=franka algo=ppo` 这种）。
- **可视化** (`viz/`)、**CLI**、**日志**、**测试**。

## 3. "谁现成、谁我们写" 一览表

| 功能 | 谁提供 |
| --- | --- |
| 物理仿真、N 路并行 step、相机渲染、机器人模型加载 | **Genesis**（现成） |
| PPO / SAC 等算法实现 + 算法侧训练循环 | **rsl-rl**（现成，需适配 env 接口） |
| 把场景搭起来、定义任务、定义动作语义、定义观测 | **TopoGym** |
| 把 env 和 policy 接起来、并行跑、自动 reset | **TopoGym**（runtime） |
| 训完之后的离线采数据 + 评测 + 出报告 | **TopoGym** |

## 4. 我们要物理化哪些任务（取自 topobench 的拓扑任务）

只列拓扑性强、适合做机器人 manipulation 的：

| 任务 | 拓扑性质 | 机器人要做什么 | 形变体? |
| --- | --- | --- | --- |
| `knots_untangle` | 纽结交叉数 | 抓绳端点拖到另一格 | ✅ 绳子 |
| `order_bead_string` | 曲线上珠子的线性序 | 抓珠子穿在绳上 | ✅ 绳子+珠子 |
| `continuity_pipe` | 管道连通分量 | 抓-转 90°-放 | ❌ 全刚体 |
| `order_swap_puzzle` | 置换距离 | 推方块到空位 | ❌ 全刚体 |
| `enclosure_chat_noir` | 边界可达性 | 抓棋子放六边格 | ❌ 全刚体 |
| `separation_one_stroke` | 平面一笔画 | 笔尖拖连续轨迹 | ❌ 准刚体 |

→ 框架先支持纯刚体类（最容易），再支持绳子类（要选 DLO solver）。

## 5. 已经拍板的事

1. **仿真器只用 Genesis**，不抽象多 backend。
2. **不消费 topobench 的资产/前端**，只在概念层借鉴关卡设计。
3. **TopoGym 不反向依赖 topobench**（不 `import topobench`）。
4. **在线 RL MVP 走 rsl-rl + PPO**，但用一层抽象隔开，将来可换 RLinf / TorchRL。
5. **暂不使用 Genesis 的可微仿真**（`grad/`，只对 MPM 稳定，我们用不上）。
6. **并行用 Genesis 的 GPU 原生 n_envs**，不用 Python 多进程。

## 6. 暂时没敲定、但不阻塞框架的"默认值"

每个盒子先把接口/协议留好，默认实现给最简 stub，等第一个任务上线再敲：

- 绳子用 PBD 还是 FEM？（盒子 A）
- 默认动作接口选关节角 / 末端位姿 / 高层原语？（盒子 C）
- 默认几个相机、什么分辨率？（盒子 D）
- 离线数据落盘用 HDF5 / LeRobot / RLDS？（盒子 G - 数据模式）
- 要不要上多 GPU / RLinf？（盒子 F）

## 7. 建议的下一步（最小可行验证）

挑一个最简单的任务（比如 `order_swap_puzzle` 的物理版，纯刚体最好搞），把 A → H 八个盒子各做一个**最薄实现**，跑通：

> "用 rsl-rl 训一个 PPO，把方块滑到目标位置。"

一旦这条 end-to-end 链路通了，框架的形状就立住了，后面 knot / pipe / chat_noir 等任务都是往同样的盒子里填血肉。
